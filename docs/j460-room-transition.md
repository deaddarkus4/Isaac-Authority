Все применённые состояния совпали с кадрами хоста побитово как float32, ни один снимок не применён в чужой комнате, обе игры закончили в комнате 97, уровни не изменились, слоты обновления игрока и слезы восстановлены. `StartRoomTransition` впервые вызван в живой игре в маршруте `request`: ABI, найденный дизассемблированием, подтвердился. Summary: `room-20260919-213220-029317` (`door`) и `room-20260919-213344-724054` (`request`) в `Binaries/diagnostics/room/`; их SHA256 записаны в `installation.json`.

До этого три прогона не прошли; каждый дал исправление теста или адаптера — см. «Живые прогоны».

Предыдущий этап: [жизненный цикл обычных слёз](j460-world-tears-test.md). Там смена epoch была искусственным пакетом; здесь HOST действительно проходит в дверь, а REPLICA загружает ту же комнату.

## Почему сначала seed

Только чтение двух запущенных игр (HOST PID 42680, REPLICA PID 12800) показало ожидаемое: уровни разные.

| | HOST | REPLICA |
| --- | --- | --- |
| Seed забега | `CZH4 8E6W` (446746862) | `2PBN A7CZ` (3433938825) |
| Комнат на этаже | 15 | 11 |
| Обычные соседи стартовой комнаты 84 | справа 85, снизу 97 | слева 83, сверху 71 |

Совпадает только пустая стартовая комната, поэтому переход «в ту же комнату» без общего seed невозможен. На этом этапе **одинаковый seed — проверяемое предусловие теста**, а не нативный вызов: REPLICA начинает штатный забег игры с seed HOST.

### Один seed — всё равно разные уровни

После того как REPLICA начала забег с `CZH4 8E6W`, карта этажа совпала (те же 15 ячеек сетки), но **5 комнат из 15 различаются** — из-за разных сохранений (у REPLICA чистый профиль):

| Ячейка | HOST | REPLICA |
| --- | --- | --- |
| 83 | мини-босс, вариант 2037 | обычная, вариант 640 |
| 85 | обычная, вариант 1071 | мини-босс, вариант 2037 |
| 109 | обычная, вариант 638 | обычная, вариант 1052 |
| 126 (босс) | вариант 4013, подтип 9 | вариант 2013, подтип 13 |
| 138 (магазин) | вариант 14, подтип 1 | вариант 0, подтип 0 |

Seed генерации (spawnSeed) у переставленных комнат переезжает вместе с комнатой. Правая дверь стартовой комнаты ведёт в разные комнаты, нижняя (97) — в одинаковую. Поэтому тест требует совпадения не всего уровня, а seed, текущей комнаты и комнаты назначения; остальные расхождения записываются в отчёт (`divergentRoomsFromDifferentSaves`). Безопасность обеспечивает не тест, а нативная сверка: реплика не пойдёт в комнату, которая у неё отличается от описанной хостом. **Для полного совпадения уровней клиенту нужно то же сохранение, что и хосту.** Штатный онлайн, судя по журналам десинков, сверяет контрольные суммы общего сохранения; как именно он его передаёт, не исследовано.

Нативный путь найден, но сознательно не используется: `Console::RunCommand` (RVA `0x28cdc0`, `this` = `Game+0x68d78`) — так работает `Isaac.ExecuteCommand`. Команда `seed` перезапускает забег, а точка, из которой это безопасно делать, не установлена; вызывать её изнутри обновления игрока нельзя считать безопасным. Это статический кандидат для автоматизации позднее.

Игры используют разные сохранения (у REPLICA чистый изолированный профиль). Если генерация этажа зависит от открытого контента, одинаковый seed может дать разные уровни. Тест это обнаружит и откажется запускаться; тогда потребуется общий файл сохранения.

## Что найдено в J460

LuaBridge регистрирует методы прямыми указателями на нативные функции (`PUSH функция; PUSH имя; CALL регистратор`), поэтому имя метода Lua API даёт адрес. `reverse/ghidra/ExportIsaacRoom.java` принимает `name:Метод` или RVA, сам разрешает имя и декомпилирует функцию. Результаты: `Binaries/research/j460-room*/`.

| Назначение | Адрес или смещение |
| --- | --- |
| `Game::StartRoomTransition(roomIdx, direction, animation, player, dimension)` | RVA `0x2fd7c0`, x86 thiscall, `ret 0x14` |
| Ядро `RoomTransition::Start` | RVA `0x42ee40`, `this` = `Game+0x1b83c` |
| Поля `RoomTransition`: режим / направление / цель / измерение / анимация | `+0x0` / `+0x10` / `+0x14` / `+0x18` / `+0x1c` |
| `Game::ChangeRoom` / `Level::ChangeRoom` (немедленная загрузка) | RVA `0x2fe2f0` / `0x33fc80` — не вызываются |
| `Game::GetSeeds` / стартовый seed | `Game+0x1bb84` / `Game+0x1bb88` |
| Разбор строки seed / `Seeds::SetStartSeed(uint)` | RVA `0x5eb6b0` / `0x5eb880` |
| Количество комнат / дескрипторы / таблица поиска | `Game+0x182cc` / `Game+0x14`, шаг `0xb8` / `Game+0x17adc` |

`StartRoomTransition` проверяет диапазоны и вызывает ядро, которое **только записывает запрос** (цель, направление, анимацию, таймер 3 или 7 кадров), обнуляет скорости игроков и ставит режим 1. Саму комнату игра загружает позже в собственном цикле. Так же поступают двери, поэтому запрос изнутри обновления игрока соответствует штатному порядку. Ядро молча игнорирует запрос, если `Game+0x1ba78 != 0`; поэтому после вызова модуль перечитывает режим и цель.

Формат seed восстановлен из `0x5eb6b0`: алфавит `ABCDEFGHJKLMNPQRSTWXYZ01234V6789`, шесть символов дают старшие 30 бит, седьмой — два младших бита и три бита контрольной суммы, восьмой — остальные пять; значение складывается с `0x0fef7ffd` по XOR, контрольная сумма считается по итоговому seed. Обе пары из журналов самой игры (`CZH4 8E6W` = 446746862, `2PBN A7CZ` = 3433938825) воспроизводятся в обе стороны — это юнит-тест.

## Реализация

Новые модули `IsaacAuthorityRoomSource.dll` и `IsaacAuthorityRoomReplica.dll` собираются из того же `world_adapter.cpp` с флагом `ISAAC_WORLD_ROOMS`. Модули слёз 0.4 собираются без флага и сохраняют проверенное поведение. Формат WLD1 не менялся: ключ комнаты уже был в каждом пакете.

Источник при смене комнаты по-прежнему увеличивает epoch и сбрасывает ID. Добавлен допуск: если контекст не читается во время загрузки (до 90 обновлений подряд), он ничего не публикует и не останавливается.

Реплика для каждого свежего снимка выбирает один из трёх путей (`Decide`, чистая функция в `world_state.cpp`):

- **Apply** — хост в той же комнате и том же поколении: состояние применяется как раньше.
- **Restart** — та же комната, но новое поколение хоста (он выходил и вернулся): старые копии удаляются, снимок применяется как первый.
- **Travel** — хост в другой комнате. Реплика находит эту комнату в собственном уровне и сверяет stage, stageType, индекс, измерение, тип, вариант, форму и spawnSeed. Несовпадение — `levelMismatch` и остановка: идти в комнату, которую хост не описывал, нельзя. Затем удаляются копии слёз, вызывается `StartRoomTransition` с анимацией fade и направлением двери (для соседних одиночных комнат, иначе −1), результат перечитывается.

Кроме того, локальная комната реплики может смениться **без запроса модуля**: подавление обновления игрока не отключает двери, и игрока, удерживаемого в проёме в позиции хоста, проносит собственная игра реплики (см. «Живые прогоны»). Это не чужой контекст, а новое место: модуль забывает копии слёз (уничтоженные игрой считаются отдельно, `vanished`), принимает новую комнату и продолжает следовать за хостом (действие 5, счётчик `selfMoves`). Снимки поколения хоста, за которым реплика шла до этого, в течение 1,5 с не вызывают обратного перехода (`settled`): они описывают комнату, из которой обе игры только что вышли. Если хост на самом деле остался там, реплика вернётся по истечении окна.

В пути оригинальное обновление игрока не подавляется — переходом владеет игра. Снимки не применяются, пока локальный ключ комнаты не совпадёт с целью; после прибытия применение начинается заново с пустого набора. Лимит ожидания 5 секунд, затем ошибка и остановка. Счётчик посещений в сравнение мест не входит: это локальная история каждой игры.

В журнале реплики добавлены действия 3 (переход запрошен) и 4 (комната достигнута), в итоговой записи — `transitions`, `arrivals`, `levelMismatches`, `traveling`.

## Живые прогоны

HOST PID 42680, REPLICA PID 12800, seed `CZH4 8E6W`, дверь вниз (84 → 97). Во всех прогонах, включая неудачные, очистка прошла, слоты обновления игрока и слезы восстановлены, ошибок модулей (`faults`) нет. Артефакты: `Binaries/diagnostics/room/`. Первые три прогона не прошли:

| Прогон | Что произошло | Исправление |
| --- | --- | --- |
| `room-20260919-211804` | Источник подключился, но не записал ни одного кадра: HOST стоял на паузе (`PauseOnFocusLost=1`): при потере фокуса он открывает меню паузы, и возврат фокуса его не закрывает. Реплика не подключалась, клавиши не нажимались. | Тест подключает модули только к идущей игре (счётчик кадров `Game+0x264f8`) и сам закрывает меню паузы — см. «Пауза, смерть и перезапуск». |
| `room-20260919-212014` | 542 снимка применены с побитовым совпадением, 2 слезы созданы и удалены. HOST не дошёл до двери: стоял на x = 380 вместо 320 (остаток прежних тестов) и упёрся в стену рядом с проёмом (y = 410). | Тест сначала выравнивает игрока по оси двери по опубликованной позиции, затем идёт. |
| `room-20260919-212119` | HOST прошёл в дверь: последний кадр комнаты 84 на 4141 мс, первый кадр комнаты 97 (epoch 2, позиция 320×160) на 4203 мс — обновление игрока не прерывается на время перехода. Реплика применила 222 снимка и остановилась на 4125 мс со счётчиками `contextChanges=1, transitions=0, faults=0`. **Обе игры оказались в комнате 97.** | См. ниже. |

Третий прогон дал главный результат этапа. Реплика удерживала игрока в позиции хоста, последняя из них — в дверном проёме (326,8 × 440,7; стена на y = 410). Собственная логика двери игры-реплики сама начала переход, хотя оригинальное обновление игрока было подавлено. Локальная комната сменилась раньше, чем пришёл первый снимок хоста из новой комнаты, и модуль остановился как при чужом контексте. То есть дверь срабатывает вне подавляемой функции обновления игрока, и **для обычных дверей переход реплики происходит сам** — запрос `StartRoomTransition` нужен там, где реплика в проём не попадает: потеря пакетов у двери, телепорты, люки.

Попутно измерено: обновление игрока вызывается 60 раз в секунду (249 кадров источника за 4141 мс), а не 30, как остальная логика.

После исправления адаптера оба маршрута прошли с первого раза (таблица в начале документа). В маршруте `request` реплика держала игрока на y = 397,6, собственная дверь не сработала, и первый же снимок из комнаты 97 привёл к запросу перехода: действие 3 на 3437 мс, действие 4 на 3765 мс.

### Пауза, смерть и перезапуск

Состояние окон оказалось главным источником сбоев теста, не модулей:

- HOST (`PauseOnFocusLost=1`) при потере фокуса открывает меню паузы и держит его после возврата фокуса. REPLICA (`PauseOnFocusLost=0`) не останавливается никогда, враги у каждой игры свои — в комнате за дверью её Айзек погибает за время разбора результатов; HOST погибал так же, пока окно было в фокусе.
- Оба признака — входы `Game::IsPaused` (RVA `0x2fd350`): `Game+0x23a74` равно 1 при открытом меню паузы, `Game+0x1d520` равно 2 на экране смерти, в игре оба нулевые; `Manager+8` равно 2 в забеге и 1 в главном меню. Меню паузы открывается не сразу после возврата фокуса, поэтому тест опрашивает признак, пока кадры не пойдут. Первая догадка (`0x1d520` — меню паузы) была неверной: замер сделан, когда HOST уже стоял на экране смерти.
- На экране смерти Esc означает выход в главное меню. Промежуточная версия теста нажимала Esc по одному признаку «кадры не идут» и **вывела REPLICA с экрана смерти в главное меню**; забег восстановлен автоматизацией меню (New Run → Tab → seed → Enter). Теперь Esc отправляется только если игра в забеге, меню паузы открыто, экрана смерти нет **и игрок жив** (`Entity+0x172/+0x173`); на экране смерти перезапуск идёт клавишей Space, в остальных случаях — удержанием R до сброса счётчика кадров.
- Забег, начатый с введённым seed, сохраняет его при перезапуске; обычный — нет. Оба забега сейчас начаты с `CZH4 8E6W`, поэтому `--restart-runs` возвращает обе игры в исходное состояние без ручных действий.
- Затемнённый экран HOST — проклятие темноты этого seed, а не признак паузы. Паузу определять только по счётчику кадров.

## Живой тест

`scripts/Test-IsaacRoom.py` (маршрут `--route door` по умолчанию или `--route request`):

1. Только чтением сверяет seed, stage, текущую комнату и комнаты за дверями; обе игры должны стоять в стартовой комнате без идущего перехода. `--check` выполняет только этот шаг и ничего не подключает. `--restart-runs` перед этим удерживает R в обеих играх до перезапуска забега (seed сохраняется только у забегов, начатых с введённым seed).
2. Выбирает дверь, за которой в обеих играх одна и та же обычная одиночная комната (или `--direction`).
3. Ждёт, пока обе игры реально идут. HOST стреляет в первой комнате, выравнивается по оси двери и идёт в неё (WASD). Клавиши отпускаются, когда источник публикует новую комнату.
4. `door`: ничего не задерживается; реплику должна пронести её собственная дверь — ровно одно `selfMoves`, ни одного запроса. `request`: снимки на последнем отрезке перед стеной не передаются (потеря пакетов у двери), реплика остаётся вне проёма и должна запросить и завершить ровно один переход. Затем HOST стреляет уже в новой комнате.
5. Проверки: побитовое совпадение float32 всех применённых снимков с кадрами хоста по обе стороны двери, слёзы по обе стороны, `created == removed + vanished`, ни один снимок не применён в чужой комнате, обе игры закончили в комнате назначения, уровни не изменились, слоты обновления восстановлены.

```powershell
.\scripts\Build-IsaacAuthority.ps1
python -m unittest discover -s scripts/tests -p test_*.py
.\scripts\Install-IsaacRoom.ps1
python scripts/Test-IsaacRoom.py --source-pid <HOST_PID> --replica-pid <REPLICA_PID> --check
python scripts/Test-IsaacRoom.py --source-pid <HOST_PID> --replica-pid <REPLICA_PID> --binary-directory '<папка игры>\IsaacAuthority\Room'
```

Тест управляет окном HOST около 12 секунд; окна не переключать. За дверью обычная комната с врагами: после теста HOST остаётся в ней с закрытыми дверями. Враги не синхронизируются, у каждой игры они свои; REPLICA без паузы в такой комнате со временем погибает.

Установщик кладёт DLL под именами с коротким хешем содержимого (`IsaacAuthorityRoomReplica-e87b4b5e.dll`), имена записаны в `installation.json`, тест берёт их оттуда. Загруженный модуль заблокирован и закреплён в процессе до выхода из игры, а инжектор различает модули по имени файла; именованные по содержимому копии позволяют загрузить новую сборку рядом со старой, неактивной, без перезапуска игр. Прежняя проверка «модуль загружен» в установщиках из 64-битного PowerShell не видит модулей 32-битной игры и ничего не защищала.

**10/10 CTest и 21/21 Python-тестов проходят.** Новое покрытие: идентичность места без счётчика посещений, три пути реплики, направление двери и отсутствие переноса через край сетки, контракт двух новых DLL, текст seed по журналам игры, сравнение уровней, выбор двери.

## Ограничения

- Проверен один переход через одну дверь (вниз, 84 → 97) в одном забеге, по одному прогону на маршрут. Окно `settled` и учёт `vanished` в этих прогонах не понадобились (оба счётчика 0): ветки собраны и покрыты только логикой, не живой игрой. Обратный переход, несколько переходов подряд, большие комнаты, телепорты и люки не проверялись.
- Для повторяемых тестов оба забега должны быть начаты с введённым seed: только тогда рестарт (R или Space после смерти) его сохраняет.
- Поддержаны обычные комнаты сетки 13×13 в измерении 0. Специальные комнаты с отрицательными индексами источник не описывает; большие комнаты описываются, но направление двери для них не вычисляется.
- Обратный переход не тестируется: двери закрыты, пока живы враги.
- Остановка реплики во время перехода вернёт ошибку: очистка исполняется только на обновлении игрока.
- Согласование seed ручное. Сохранения, предметы, враги, урон, ввод клиента и интернет-транспорт по-прежнему не синхронизированы.
