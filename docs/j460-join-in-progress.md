## Что есть в игре (статический разбор J460)

Сетевой менеджер — `Manager+0x4b3d8` (`Manager` — глобальный указатель RVA `0x87169c`); его текущий кадр — `+0xc`.

| Что | Где (RVA) | Что делает |
| --- | --- | --- |
| Признак «в лобби идёт игра» | данные лобби `current_stage` ≥ 1 | меню Quick Match (`0x4e64f0`), найдя только такие лобби, само спрашивает: «создать новое» или **«войти в идущую»** (`JOIN_LOBBY_IN_PROGRESS`, `ONLY_FOUND_JOIN_IN_PROGRESS`) |
| Лобби входящего | меню лобби `0x4e8af0` | вместо отсчёта старта — `#GAME_IN_PROGRESS` и статус забега хоста («Exploring Cellar I»), который приходит сообщением «Run Status» |
| Приёмник сообщений лобби | `0x516770` | виды: 0 «Player Info», 2 «Save Data», 3 «Save Data Request», 4 «Join New Game», 5 «Join Existing Game», 7 «Report Game States» (ещё «Run Status», «Seed Info») |
| Очередь входа | «Player Info» (вид 0) во время игры от участника лобби, которого нет в составе матча, **с поднятым битом 2 во флагах (это «готов», Tab в лобби)** → `Adding pending join for player`; очередь — `std::map` по id в `netmanager+0x1864`, размер `+0x1868` | вошедший встаёт в очередь у **каждого** участника матча, не только у хоста |
| Когда впускают | `NetManager::process_pending_joins` `0x50df40` (`thiscall`, один аргумент «принудительно») — зовётся из автомата экрана перехода этажа (`0x52f1c0`), из записи состояния на новом этаже (`0x558cb0`) и дважды из кода `Game` около `0x2fb2xx` | **на смене этажа**: каждый участник добавляет новых игроков (`0x50d9b0`, `Adding %d new players`), а владелец лобби сохраняет `GameState` и шлёт вошедшим стартовое сообщение вида 5 |
| Стартовое сообщение вида 5 | читатель `0x517fd0` (`Joining existing game on frame %d`) | кадр входа → `Manager+0x4b3e4`; состав игроков (id, тип персонажа и т. п., записи по `0x14` в `Manager+0x4b278`); **сжатый `GameState`**, читается `GameState::read` с `isLocalRun = false` (то самое «вход в существующий онлайн-матч» из заметок REPENTOGON); статистика кооператива; **состояние общего генератора случайных чисел целиком** (`0x270` слов в `0xc7ac70`); чётность кадра, счётчики; затем штатный старт сетевого матча `0x50e2a0` с этим состоянием |
| Общий вход обоих видов | `NetManager::notify_game_start` `0x50ca40` | вид 4 — обычный старт из лобби (`0x517a50`), вид 5 — вход в идущую; после любого — общее сохранение поверх своего и `PersistentGameData ReadOnly = false` |

Вывод: вошедший получает от хоста мир целиком (`GameState`), общее сохранение сессии и генератор, и начинает считать кадры с общего кадра — ровно то, что нам пришлось бы писать самим. **Штатно входящий получает общее сохранение сессии как есть, без проверки своего** — правило пользователя строже штатного.

## Правило пользователя: кто может войти

Сессия делит те анлоки, которые есть у **всех** её участников (сборщик общего сохранения `0x51a450`: флаги — побитовое И). Входящий годится, если в его сохранении есть каждый такой анлок; больше — можно, счётчики (пожертвования, уровень магазина) не спрашиваются. Упакованное сохранение участника (писатель `0x51b130`) начинается с достижений: 642 флага по биту, младший первым, 81 байт.

- Чистая логика — `native_state`: `SharedUnlocks` (И по достижениям участников) и `UnlocksLacking` (сколько анлоков сессии у сохранения нет; 0 — можно). Тесты — CTest `native_exchange`.
- То же в Python: `isaac_save.py joinable --joiner <сохранение> <сохранения участников…>` называет недостающие достижения. На настоящих файлах: сессия «пользователь + друг» делит 100 анлоков, сохранение пользователя входит (не хватает 0); в сессию одного друга ему не хватило бы 123, другу в сессию одного пользователя — 6.

## Где это проверяется: у каждого участника, внутри штатной обработки очереди

Прочитано в живой памяти трёх игр пробы 1 (`Binaries/native-test-results/probes/saves_probe.py`, только чтение):

| Что | Где | Что увидено |
| --- | --- | --- |
| Сохранения участников лобби | `std::map` по id в `netmanager+0x1068` (размер `+0x106c`); узел: ключ `+0x10`, значение `+0x18`, **достижения — 642 байта по `значение+0x38`** (как в живом `PersistentGameData`) | у A, B и **у входящего C** по 3 записи; массивы A и C побайтно равны сохранению пользователя, B — копии сохранения друга |
| Состав матча | записи по `0x14` в `Manager+0x4b278…+0x4b27c`; пользователь записи `+4`, его id `+8` | у A и B одни и те же два id; у C пусто |
| Очередь входа | `std::map` по id в `netmanager+0x1864` (размер `+0x1868`) | у A и B по одной записи — id C (`0xfefefefe` над дескриптором его окна) |
| Удаление из очереди | `0x513c80` — `erase(ключ)` этой карты (`thiscall`, `ret 4`); игра зовёт его сама, когда стоящий в очереди снимает «готов» | прочитано в декомпиляции |

Отсюда решение: **словари у всех участников одинаковы, значит каждый выносит один и тот же вердикт сам, без обмена по сети.** Модуль (правило `join`, бит 18; у хоста и гостей одинаково, маски правил сверяет рукопожатие) перехватывает штатную `process_pending_joins` (`0x50df40`; первые пять байт — три целые инструкции — заменяются переходом, как у `TriggerClear`) и перед её выполнением считает анлоки сессии по игрокам матча, сверяет сохранение каждого стоящего в очереди и недопущенных убирает штатным `erase`. Дальше игра впускает оставшихся сама. Входящий, чьё сохранение участникам неизвестно, не впускается; если неизвестно сохранение кого-то из игроков матча, очередь не трогается (`joinsUnjudged`). Счётчики `joinsAdmitted` / `joinsRefused` / `joinLacking` — в стенде и в `.status`. «Кик» не понадобился: штатный — это голосование против игрока матча (`VoteToDrop` `0x509c40`) и бан через данные лобби (`0x50a150`, `lobby_banned`), для сидящего в лобби слишком грубо, а на локальном сервисе данных лобби нет вовсе.

**Собрано в `Binaries/authority-check` (12/12 CTest, `/W4 /WX`), 55/55 Python; живьём НЕ проверено; основная сборка не пересобрана — открыты тестовые игры.**

## Что ещё должен уметь наш модуль

1. **Смена состава — не только уход, но и приход.** Сделано: разбор журнала считает сменой состава и строку `Adding remote player` посреди матча (`MatchLog::roster`), так что установленный модуль перезапускается с новым соседом так же, как при уходе игрока (сверка контрольных сумм остаётся выключенной). У вошедшего модуль стартует обычным путём — по своему `Start Networked`. *Живьём не проверено; пишет ли вошедший `Start Networked`, покажет конец пробы 1.*
2. **Стенд на троих.** Сейчас тестовая пара называет соседа адресом, и сосед один. Нужно: `peer=IP:PORT@ID` (id локального сервиса — `0xfefefefe` над дескриптором окна) и выбор соседей по составу матча из журнала — как под Steam; стенд пишет конфигурацию всем трём сразу, модуль C ждёт своего матча. *Не сделано.*
3. **Входящий без модуля.** Не отличается: рукопожатие с ним не состоится, через 60 с модули сдадутся и вернут сверку контрольных сумм разошедшимся играм — матч расколется у всех. Нужно решение хоста, разосланное гостям в снимке мира заранее (вердикт «модуль ответил» у разных участников не детерминирован): id входящего известен из журнала (`User … joined lobby`), модуль хоста спрашивает его модуль тем же каналом (Steam, канал 7460); у входящего модуль загружен игрой и вне матча. *Не сделано.*
4. **Подсказка входящему.** У него есть сохранения обоих участников — его модуль может сам посчитать, чего не хватает, и написать это в заголовке окна, а не оставлять его перед «GAME IN PROGRESS». *Не сделано.*

## Открыто

- Впуск на смене этажа вживую (проба 1 не закончена); пишет ли вошедший `Start Networked` и как нумеруются устройства у трёх игр.
- Под Steam после старта лобби может закрываться для входа (`joinable` / `not joinable`, «Force Restart is setting Lobby Visibility to PRIVATE») — по словам пользователя, в штатном онлайне войти посреди забега нельзя; что именно этому мешает в Friend Match, не выяснено. Если лобби закрыто, модуль хоста должен держать его открытым (это данные лобби, не код синхронизации).
- Остальные гости в момент впуска **не** получают `GameState` хоста; в нашей модели они и так расходятся с хостом в несинхронизируемом, это не хуже прежнего.
