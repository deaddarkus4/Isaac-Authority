# Сохранение лобби: пересечение прогресса всех участников

**20 сентября 2026, 00:30–00:42 UTC.** Поправка пользователя, знающего штатный онлайн из первых рук, к [общему сохранению](j460-shared-save.md) и [входу в забег](j460-run-join.md):

1. **В штатном онлайне нельзя войти посреди забега.** Всё решается в лобби при старте.
2. **Ограничения подстраиваются под игроков лобби.** Если предмет не открыт хотя бы у одного, он не появится ни у кого; то же с боссами, с уровнем магазина и числом пожертвованных монет.

Мой прежний вывод «сохранение одного участника рассылается всем» был неверен; он стоял в двух документах как догадка по строкам и там зачёркнут. Следствие для архитектуры: **все участники, включая хоста, играют с одного объединённого сохранения**. Значит, и хост — изолированный экземпляр с копией, а не основная игра пользователя; что так работает, [уже показано](j460-run-join.md).

## Формат сохранения (J460)

Загрузчик — RVA `0x526f10`; результаты Ghidra — `Binaries/research/j460-save-checksum*/`.

| Часть | Содержимое |
| --- | --- |
| Заголовок | 16 байт `ISAACNGSAVE09R  ` |
| Слово | 4 байта, загрузчик сохраняет его без проверки (`+0xf84` объекта) |
| Блоки 1–10 | по 12 байт заголовка — тип, слово размера, число элементов — и элементы. Всегда заканчиваются на байте 4016 |
| Блок 11 | бестиарий, переменной длины (48 байт у чистого сохранения, 4392 у сохранения пользователя) |
| Контрольная сумма | последние 4 байта |

| Блок | Что | Элементов | Байт на элемент |
| --- | --- | --- | --- |
| 1 | достижения (они же открытые предметы, персонажи, уровни магазина) | 642 | 1 |
| 2 | счётчики (в том числе пожертвования) | 523 | 4 |
| 3 | счётчики этажей | 14 | 4 |
| 4 | предметы | 733 | 1 |
| 5 | мини-боссы | 7 | 1 |
| 6 | боссы | 104 | 1 |
| 7 | испытания | 46 | 1 |
| 8 | счётчики заставок | 27 | 4 |
| 9 | настройки игры | 2 | 4 |
| 10 | счётчики особых seed | 80 | 1 |

Слово размера блока — не длина в байтах: у всех блоков, кроме первого, оно равно учетверённому числу элементов, даже когда элемент занимает байт.

**Контрольная сумма** (RVA `0x283580` — диапазон, `0x283410` — алгоритм): по байтам от 16-го до начала самой суммы; CRC-32 с полиномом `0xEDB88320`, затравка `0xFEDCBA76` с инверсией до и после, **но таблица строится не так, как стандартная**: первый сдвиг логический, остальные семь — арифметические, со знаком. Из-за этого ни стандартный CRC-32, ни известный по редакторам сохранений вариант не подходят (`TABLE[1] = 0x09073096` вместо `0x77073096`). Реализация сверена на четырёх настоящих файлах J460: сумма совпала, разбор и сборка побайтно точны.

## Правило объединения

`scripts/isaac_save.py merge --output <файл> <сохранение хоста> <сохранения гостей…>`: **каждый флаг и каждый счётчик становится наименьшим из значений участников.** Для флагов это «открыто у всех», для счётчиков — «как у наименее продвинувшегося» (пожертвования в магазин и подобное). Настройки игры, бестиарий и непроверяемое слово — ничей не прогресс, берутся у первого файла, хоста. Исходные файлы только читаются; существующий файл инструмент не перезаписывает.

Это правило — приближение к описанному пользователем поведению, а не разобранный код игры: что именно и как объединяет штатный онлайн, в бинарнике не выяснялось.

## Живая проверка

Объединение сохранения пользователя (открыто 90 достижений из 642, 190 предметов, 51 босс) с чистым даёт нули во всём прогрессе, но файл при этом другой, чем чистый: 8412 байт с бестиарием и настройками хоста и с нашей контрольной суммой. С ним запущен пятый изолированный экземпляр, тот же seed `CZH4 8E6W`, Isaac, hard:

| | Результат |
| --- | --- |
| Принял ли файл загрузчик | да: в журнале нет `checksum invalid`, слот 1 выглядит пустым, остальные персонажи под замком, серия побед 0 |
| Сложность на экране персонажа | hard — пришла из настроек хоста |
| Уровень относительно игры с чистым сохранением | **0 комнат из 15 отличаются**, проклятия нет у обеих |
| Уровень относительно HOST с полным сохранением | те же 5 комнат (83, 85, 109, 126, 138) и проклятие Darkness только у HOST |

Игра принимает файл, записанный нами, и уровень определяется объединённым прогрессом. После проверки пятый экземпляр закрыт обычным закрытием окна.

При вводе seed в этом экземпляре набралось только три символа из восьми — набор попал на анимацию открытия экрана; это показал снимок окна до подтверждения, недостающие символы довведены. Два шага меню перед этим я нажал подряд без снимка между ними — так делать нельзя, даже когда последовательность уже проверена.

**39/39 Python-тестов**: контрольная сумма (значения таблицы, отличные от стандартных), побайтный круговой проход, порча файла и неверный порядок блоков, объединение трёх сохранений (достижения — открытое у всех, пожертвования — наименьшее, порядок гостей не важен, настройки и бестиарий хоста), отказ объединять сохранения другой раскладки.

## Как теперь собирается лобби

```powershell
python scripts/isaac_save.py info <сохранение>                       # что открыто, в числах
python scripts/isaac_save.py merge --output lobby.dat <хост> <гость>  # общее сохранение лобби
.\scripts\Start-IsaacReplica.ps1 -PersistentGameData lobby.dat        # так запускается КАЖДЫЙ участник, хост тоже
```

## Ограничения

- Проверено объединение только с чистым сохранением — оно даёт нули, то есть самый простой случай. Частичного пересечения двух продвинутых сохранений под рукой нет; юнит-тест его покрывает, игра — нет.
- Неизвестно, все ли счётчики блока 2 влияют на генерацию и верно ли для каждого правило минимума; для прогресса, который *убирает* что-то из игры, минимум был бы неверен. Таких случаев не найдено, но и не искалось.
- Бестиарий и предметы коллекции (блок 4) на генерацию, по всей видимости, не влияют; объединяются по общему правилу ради единообразия.
- Сохранение лобби — это запуск экземпляров. Войти в идущий забег штатный онлайн не даёт; у нас это возможно [переносом файла состояния](j460-run-join.md), но это уже сверх паритета.
