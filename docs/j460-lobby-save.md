# Сохранение лобби: пересечение прогресса всех участников

**20 сентября 2026.** Поправка пользователя, знающего штатный онлайн из первых рук, к [общему сохранению](j460-shared-save.md) и [входу в забег](j460-run-join.md):

1. **В штатном онлайне нельзя войти посреди забега.** Всё решается в лобби при старте.
2. **Ограничения подстраиваются под игроков лобби.** Если предмет не открыт хотя бы у одного, он не появится ни у кого; то же с боссами, с уровнем магазина и числом пожертвованных монет.

Мой прежний вывод «сохранение одного участника рассылается всем» был неверен; он стоял в двух документах как догадка по строкам и там зачёркнут. Следствие для архитектуры: **все участники, включая хоста, играют с одного объединённого сохранения**. Значит, и хост — изолированный экземпляр с копией, а не основная игра пользователя; что так работает, [уже показано](j460-run-join.md).

Первая версия инструмента объединяла «по минимуму» — как приближение к описанию. По настоянию пользователя правило **прочитано из кода игры** и сверено с дампами 46 настоящих сессий; ниже — оно, а не приближение.

## Как это делает сама игра

Результаты Ghidra — `Binaries/research/j460-shared-save*/` (в git не входят).

| Шаг | Где (RVA) | Что происходит |
| --- | --- | --- |
| Участник сообщает своё сохранение | сериализатор `0x51b130` | общая часть сохранения в упакованном виде (ниже) уходит хосту; хост складывает их в словарь «id участника → сохранение» (`netmanager+0x1068`) |
| Хост запускает матч | `Menu_OnlineLobby::send_game_start` `0x4ee080` → `0x50c560` → **сборщик `0x51a450`** | из всех сообщённых сохранений строится одно общее |
| Все получают его | обработчик «Notify Game Start» `0x50ca40` → десериализатор `0x51adf0` | общее сохранение ложится **поверх** живого `PersistentGameData` (`Manager+0x14`); то, чего в нём нет, остаётся своим |
| Во время матча | контрольная точка `0x519440` | файл `sharedsave<слот>.dat`: общее сохранение на старте и его текущее состояние |
| Конец сессии | обратная запись `0x519980` | настоящее сохранение перечитывается и получает заработанное за сессию; затем пишутся дампы `online_logs/sessions/<сессия>/` |

### Правило сборщика (`0x51a450`)

Накопитель заполняется единицами (`0xFFFFFFFF` для счётчиков, `0x7FFFFFFF` для счётчиков заставок), затем по очереди обрабатывается сохранение каждого участника:

| Часть | Правило |
| --- | --- |
| достижения, предметы, мини-боссы, боссы, испытания | побитовое **И**: флаг остаётся, только если он есть у всех |
| счётчики (523) и счётчики этажей (14) | **наименьшее**, сравнение беззнаковое |
| счётчики заставок (27) | наименьшее, сравнение **знаковое** |
| бестиарий, карты 1 и 2 | по каждому ключу наименьшее значение; ключ, которого нет **хотя бы у одного** участника, удаляется |
| в конце | id участников (до четырёх), чьи сохранения вошли |

**В общее сохранение не входят** настройки игры (блок 9), счётчики особых seed (блок 10) и карты 3–4 бестиария: в штатном онлайне они у каждого свои. Раз игра на lockstep при этом не расходится, на симуляцию они не влияют — поэтому у нас их можно без вреда взять у хоста.

### Упакованный вид (то, что ходит по сети и лежит в дампах)

Порядок: достижения, счётчики, предметы, счётчики этажей, мини-боссы, боссы, счётчики заставок, испытания; затем две карты бестиария (число записей и записи по 8 байт: ключ со знаком, значение) и 32 байта id участников. Флаги пакуются по биту, младший бит первым, в `(число >> 3) + 1` байт (упаковщик `0x51b580`, читатель `0x51b650`) — то есть 104 босса занимают 14 байт, а не 13. Неизменная часть — 2450 байт.

### Обратная запись (`0x519980`)

Флаги: `свой |= общий_в_конце`. Счётчики, счётчики этажей и заставок, обе карты бестиария: `свой += max(0, общий_в_конце − общий_на_старте)`. Жетоны Эдема (счётчик 21) отдельно: `max(0, свой + конец − старт)` — они могут и убывать; общий цикл по счётчикам перед этим тоже проходит по счётчику 21, не начисляется ли прирост дважды — не проверялось. Перед записью контрольной точки 36 счётчиков (114, 115, 159–172, 212, 385–403) и 12 достижений (242–251, 275, 341) в обеих копиях заменяются своими значениями игрока (`0x51b720`), то есть разница по ним всегда ноль и через онлайн они не меняются. Нашему прототипу обратная запись пока не нужна — записано, чтобы не выяснять заново.

## Сверка с настоящими сессиями

В `online_logs/sessions/` пользователя 46 сессий (16–19 сентября 2026, все J460), в каждой до четырёх файлов. Только чтение; Steam id сравнивались, не печатались.

**Что на самом деле лежит в дампах** (по коду `0x519980` → `0x503040`), вопреки именам:

| Файл | Содержимое |
| --- | --- |
| `sharedsave_begin.dat` | общее сохранение на старте матча |
| `sharedsave_end.dat` | его состояние на последней контрольной точке |
| `persistentgamedata1_begin.dat` | **не** сохранение игрока до сессии, а копия живого `PersistentGameData` в момент обратной записи — то есть общий контекст в конце сессии |
| `persistentgamedata1_end.dat` | настоящее сохранение игрока после обратной записи |

**Дампы общего сохранения игра пишет из уже освобождённой памяти**: буферы освобождаются сразу после разбора, а в файл попадают позже. Поэтому 20 из 92 дампов — чужая память (в 9 виден файл сохранения, в 6 — файл состояния забега), а у уцелевших первые 4 байта (достижения 0–31) иногда затёрты указателем кучи. Это объяснило «аномалию», из-за которой общее сохранение казалось богаче своего.

| Проверка | Результат |
| --- | --- |
| файлы сохранений: разбор и побайтно точная сборка | **100 из 100** (92 из сессий, 7 изолированных экземпляров, файл Steam Cloud); во всех карты бестиария в порядке 4, 2, 3, 1, записи по возрастанию ключа, флаги только 0 и 1; `merge` одного сохранения даёт его же |
| дампы общего сохранения, разобранные точно до последнего байта | **72 из 72** уцелевших; местный игрок назван среди участников во всех 72; записи бестиария — по возрастанию ключа |
| общее сохранение на старте целиком укладывается в настоящее сохранение игрока (флаги ⊆, счётчики ≤, ключи бестиария ⊆) | **32 из 38** |
| отличие только в первых 4 байтах дампа | 3 — там `0x30a1dc48`, `0x8212b930`, `0x8ea2f898`: выровненные указатели кучи, не флаги |
| сессии с двумя стартами подряд | 2 — второе общее сохранение собрано из живых данных с прогрессом первого забега, а обратная запись видит только второй старт |
| жетон Эдема | 1 — игрок сообщил 1 жетон и сыграл этот забег за Эдема, жетон потрачен (строка журнала игры `Merging eden coins` совпадает с дампом) |

Необъяснённых расхождений нет. Точного равенства «наш `merge` = общее сохранение игры» на этих данных проверить нельзя: сохранений остальных участников у нас нет, есть только то, что результат обязан укладываться в каждое из них, — и он укладывается.

## Сверка с копиями сохранений друзей

20 сентября пользователь дал копии папки Steam Cloud двух друзей, снятые 18 сентября. Файлы распакованы только во временную папку и в репозиторий не входят; ники и Steam id здесь не приводятся, участники сопоставлены с журналами по id без печати.

| | Первый друг | Второй друг |
| --- | --- | --- |
| Файл Repentance+ | 12 996 байт: 223 достижения, 533 предмета, 86 боссов | 8 204 байта: 43 достижения, 71 предмет, 31 босс |
| Когда записан (местное время, UTC+3) | 18:04:34 — конец сессии, начатой в 14:08 UTC | 17:37 — за 27 минут до конца той же сессии |
| Что это | настоящее сохранение после обратной записи | **не настоящее сохранение, а общий контекст идущей сессии**: 14 отличающихся элементов от живых данных пользователя в конце этой сессии, 300+ от любого другого состояния |

**Первый друг.** Он участвовал в 17 сессиях до снятия копии. Во всех 17 общее сохранение на старте целиком укладывается в его копию — так же, как в настоящее сохранение пользователя; единственный элемент сверх — счётчик 497 в одной сессии (он из группы, которую игра ведёт мимо общего сохранения, см. ниже). То есть каждое из этих общих сохранений одновременно не больше сохранений **двух разных участников**, чего и требует правило «И / наименьшее». В десяти сессиях после копии сверх неё от 0 до 18 элементов — друг продолжал играть.

**Второй друг.** Его файл — снимок общего контекста, а не сохранения. На машине пользователя игра за 44 сессии ни разу не писала обычный файл сохранения между стартом матча и обратной записью — ни хостом, ни клиентом. У друга же через десять минут после этой записи записан файл обычной Repentance, так что, по всей видимости, он вышел из игры посреди сессии, и при выходе в обычный файл легли живые данные, то есть общий контекст. За полтора часа до этого и через три с лишним часа после он сообщал лобби сохранение намного богаче этой копии: общее сохранение в сессиях вдвоём с ним отличалось от пользовательского всего в 20–25 элементах и содержало 49 достижений против 43 в копии. **Это догадка по меткам времени; как было на самом деле, знает пользователь.** Для проверки правила эта копия не годится, но полезна предупреждением: копия, снятая во время сессии, — не сохранение игрока.

**Побайтное сравнение** (`isaac_save.py compare`) на этих копиях равенства не дало и не могло: ни одна не снята прямо перед сессией, где известны сохранения всех участников. Ближайший случай — сессия 17 сентября 20:57 UTC, пользователь и первый друг, копия друга на сутки позже: отличаются 4 элемента из примерно 2600 (счётчик 506 из той же группы, один предмет и два значения бестиария, которые друг набрал за эти сутки) — все в ожидаемую сторону.

**Обратная запись** проверена по цепочке сессий пользователя: `настоящее после сессии N` против правила, применённого к `настоящему после N−1` и дампам общего сохранения сессии N. 31 сессия: все флаги, предметы, боссы, бестиарий и около 515 из 523 счётчиков воспроизводятся точно; расходятся 1–6 элементов за сессию (в одной 12 — между сессиями пользователь играл один) — счётчики 21 (жетоны Эдема), 497–520 и счётчики заставок. Их игра меняет в настоящем сохранении напрямую, мимо общего (по виду — серии побед, концовки, статистика онлайна; это догадка).

### Как получить побайтное подтверждение

1. Оба закрывают игру; друг присылает свой `rep+persistentgamedata1.dat` (файл пользователя читается на месте).
2. Одна сессия вдвоём, без третьих, в том же лобби матч не перезапускать.
3. `python scripts/isaac_save.py compare --shared <сессия>/sharedsave_begin.dat <сохранение пользователя до> <сохранение друга до>` — ожидается `EQUAL` (или «equal but for the first four bytes», если дамп задет освобождением памяти).

## Формат сохранения (J460)

Загрузчик — RVA `0x526f10`; результаты Ghidra — `Binaries/research/j460-save-checksum*/`.

| Часть | Содержимое |
| --- | --- |
| Заголовок | 16 байт `ISAACNGSAVE09R  ` |
| Слово | 4 байта, загрузчик сохраняет его без проверки (`+0xf84` объекта) |
| Блоки 1–10 | по 12 байт заголовка — тип, слово размера, число элементов — и элементы. Всегда заканчиваются на байте 4016 |
| Блок 11 | бестиарий: заголовок (тип, учетверённое общее число записей, число карт = 4), затем карты — номер, учетверённое число записей, записи по 8 байт (ключ со знаком, значение). **Карты лежат в порядке 4, 2, 3, 1**, записи внутри — по возрастанию ключа |
| Хвостовое слово | 4 байта |
| Контрольная сумма | последние 4 байта |

| Блок | Что | Элементов | Байт на элемент |
| --- | --- | --- | --- |
| 1 | достижения (они же открытые предметы, персонажи, уровни магазина) | 642 | 1 |
| 2 | счётчики (21 — жетоны Эдема: совпадает со строкой журнала игры; 20 — по всей видимости, пожертвования) | 523 | 4 |
| 3 | счётчики этажей | 14 | 4 |
| 4 | предметы | 733 | 1 |
| 5 | мини-боссы | 7 | 1 |
| 6 | боссы | 104 | 1 |
| 7 | испытания | 46 | 1 |
| 8 | счётчики заставок | 27 | 4 |
| 9 | настройки игры | 2 | 4 |
| 10 | счётчики особых seed | 80 | 1 |

Слово размера блока — не длина в байтах: у всех блоков, кроме первого, оно равно учетверённому числу элементов, даже когда элемент занимает байт.

**Контрольная сумма** (RVA `0x283580` — диапазон, `0x283410` — алгоритм): по байтам от 16-го до начала самой суммы; CRC-32 с полиномом `0xEDB88320`, затравка `0xFEDCBA76` с инверсией до и после, **но таблица строится не так, как стандартная**: первый сдвиг логический, остальные семь — арифметические, со знаком. Из-за этого ни стандартный CRC-32, ни известный по редакторам сохранений вариант не подходят (`TABLE[1] = 0x09073096` вместо `0x77073096`).

## Инструмент

```powershell
python scripts/isaac_save.py info <сохранение>                       # что открыто, в числах
python scripts/isaac_save.py shared <sharedsave_begin.dat>           # то же для дампа общего сохранения игры
python scripts/isaac_save.py merge --output lobby.dat <хост> <гость>  # общее сохранение лобби по правилу игры
python scripts/isaac_save.py compare --shared <sharedsave_begin.dat> <сохранения участников…>  # дамп игры против нашего объединения
.\scripts\Start-IsaacReplica.ps1 -PersistentGameData lobby.dat        # так запускается КАЖДЫЙ участник, хост тоже
.\scripts\Start-IsaacLobby.ps1 -Saves <хост>,<гость>                  # всё это одним шагом; -MergeOnly — без запуска игр
```

`Start-IsaacLobby.ps1` объединяет сохранения участников в `Binaries/game-instances/lobby-<id>/lobby.dat`, запускает по изолированному экземпляру на участника (до четырёх, окна 960×540 плиткой), сверяет, что каждый стартовал именно с этого файла, и называет окна `Isaac Authority - LOBBY <id> #N` — номером, а не ролью: кто хост, решает тест, который к ним подключается. В `lobby.json` — хеши файлов, сколько открыто у каждого участника и сколько осталось общим.

Без запуска игр проверено на настоящем частичном пересечении — сохранение пользователя (90 достижений, 190 предметов, 51 босс) и копия первого друга (223, 533, 86): общими остались **86 достижений, 188 предметов, 51 босс**, 267 и 250 записей карт бестиария; файл пользователя не изменился. Это уже не вырожденный случай «всё или ничего». Живой запуск пары с этого файла — следующий шаг.

`merge` повторяет сборщик игры; то, чего в общем сохранении игры нет (настройки, особые seed, карты 3–4 бестиария, непроверяемое и хвостовое слова), берётся у первого файла — хоста. Исходные файлы только читаются; существующий файл инструмент не перезаписывает. `decode_shared` / `encode_shared` — упакованный вид.

**Отличие от игры, сознательное:** игра кладёт общее сохранение поверх своего у каждого участника, а у нас все стартуют с одного файла, поэтому необщие части у всех — хоста. На симуляцию они не влияют (см. выше), на экране видны разве что настройки.

**42/42 Python-теста**: контрольная сумма (значения таблицы, отличные от стандартных), побайтный круговой проход с порядком карт бестиария как в файле, порча файла, неверный порядок блоков и повтор карты, объединение трёх сохранений (флаги — открытое у всех, пожертвования — наименьшее, бестиарий — пересечение ключей с наименьшим значением, карты 3–4 и настройки хоста, порядок гостей не важен), знаковое сравнение счётчиков заставок против беззнакового у остальных, упакованный вид (14 байт на 104 босса, 2450 байт неизменной части, отказ на обрезанном и удлинённом), поэлементное сравнение с отдельным учётом первых четырёх байт дампа, отказ объединять сохранения другой раскладки.

| Уровень относительно HOST с полным сохранением | те же 5 комнат (83, 85, 109, 126, 138) и проклятие Darkness только у HOST |

Игра принимает файл, записанный нами, и уровень определяется объединённым прогрессом. После проверки пятый экземпляр закрыт обычным закрытием окна. Точное правило отличается от первой версии только бестиарием (раньше он целиком брался у хоста) и знаковым сравнением счётчиков заставок; для пары «сохранение + чистое» результат по прогрессу тот же — нули, а карты 1–2 бестиария становятся пустыми, как у игры. Повторного живого запуска после уточнения не было.

При вводе seed в этом экземпляре набралось только три символа из восьми — набор попал на анимацию открытия экрана; это показал снимок окна до подтверждения, недостающие символы довведены. Два шага меню перед этим я нажал подряд без снимка между ними — так делать нельзя, даже когда последовательность уже проверена.

## Ограничения

- Правило прочитано из кода и не противоречит ни одной из 38 проверяемых сессий, но побайтного сравнения с общим сохранением игры нет: для него нужны сохранения всех участников одной сессии.
- Живьём проверено объединение только с чистым сохранением — самый простой случай. Частичное пересечение двух продвинутых сохранений покрыто юнит-тестом, игрой — нет.
- Если матч запускается второй раз в той же сессии штатного онлайна, игра собирает общее сохранение из живых данных с прогрессом первого забега. У нас лобби — это запуск экземпляров с файла, такого случая нет; при переходе к лобби «в один шаг» его надо помнить.
- Обратной записи заработанного в настоящие сохранения участников у нас нет: экземпляры изолированы, сохранения пользователя только читаются.
- Сохранение лобби — это запуск экземпляров. Войти в идущий забег штатный онлайн не даёт; у нас это возможно [переносом файла состояния](j460-run-join.md), но это уже сверх паритета.
