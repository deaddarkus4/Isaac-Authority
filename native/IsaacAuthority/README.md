# IsaacAuthority — сетевой стенд и экспериментальный адаптер J460

Проект содержит исполняемый стенд авторитетного хоста и отдельные игровые DLL, **ещё не альтернативный мультиплеер в Isaac**. Сам `IsaacAuthorityLab` не загружает DLL в игру, не меняет EXE и не использует Steam/EOS. Движение `StepFixture` — упрощённая модель тестовой комнаты, а не восстановленная физика Isaac. Два игрока представлены координатами и скоростями; управление в стенде синтетическое.

Дополнительно реализован режим `observer`: принимает по UDP позиции и скорости настоящих игроков от внешнего read-only считывателя J460. [Проверка на живой игре и запуск](../../docs/j460-live-state-reader.md). Режимы `host/client` по-прежнему используют тестовое движение; observer не управляет вторым игровым процессом.

Текущий этап — [коррекция врагов](../../docs/j460-enemy-correction-test.md): NpcSource/NpcReplica (флаг `ISAAC_WORLD_NPCS`) передают врагов комнаты секцией версии 2 протокола WLD1; реплика сопоставляет собственных врагов по InitSeed и после их обновления записывает состояние хоста. Живой тест прошёл по двум маршрутам.

Предыдущий этап — [настоящий переход комнат](../../docs/j460-room-transition.md): RoomSource/RoomReplica собираются из того же `world_adapter.cpp` с флагом `ISAAC_WORLD_ROOMS`. Реплика находит комнату хоста в собственном уровне, сверяет её и запрашивает штатный переход игры; для этого обе игры должны идти с одним seed. Установщик — `scripts/Install-IsaacRoom.ps1`, тест — `scripts/Test-IsaacRoom.py`. **Живой тест прошёл по двум маршрутам:** реплику проносит её собственная дверь (удержание игрока в проёме двери не отключает), а при потере снимков у двери она сама вызывает `StartRoomTransition` и достигает комнаты за 328 мс; состояния по обе стороны двери совпали побитово.

Последний проверенный этап — [жизненный цикл обычных слёз](../../docs/j460-world-tears-test.md): WorldSource/WorldReplica создают, обновляют и удаляют объекты по полным снимкам, сохраняют сетевые ID и отклоняют старый epoch комнаты. Живой тест: 3 создания/удаления, 194 точных применения, удержание во время паузы передачи, очистка при контрольном новом epoch. Установщик — `scripts/Install-IsaacWorld.ps1`. Фактический переход комнаты, враги, урон и клиентский ввод ещё не синхронизированы.

Предыдущая [проверка двух настоящих игр](../../docs/j460-game-pair-test.md) использует `IsaacAuthoritySource.dll` и `IsaacAuthorityReplica.dll` только для выбранного игрока: 271 точное применение, удержание при паузе и сходимость. Установщик — `scripts/Install-IsaacGamePair.ps1`; отдельная игра с изолированным профилем запускается `scripts/Start-IsaacReplica.ps1`.

Предыдущие этапы: [локальный сдвиг](../../docs/j460-player-step-test.md) (`IsaacAuthorityGame.dll`) и [пять состояний от тестового отправителя](../../docs/j460-network-state-test.md) (`IsaacAuthorityNetwork.dll`). У всех модулей нет автозапуска.

## Сборка и запуск проверки

Из корня репозитория, с установленными CMake, Visual Studio 2022 C++ и Python 3:

```powershell
.\scripts\Build-IsaacAuthority.ps1
```

Скрипт собирает x86 Release и запускает десять CTest-проверок. Двадцать две Python-проверки запускаются отдельно: `python -m unittest discover -s scripts/tests -p test_*.py`. Исполняемый файл исходного стенда: `Binaries/authority-build/Release/IsaacAuthorityLab.exe`. Для его повторного запуска без пересборки:

```powershell
python native/IsaacAuthority/tests/loopback.py Binaries/authority-build/Release/IsaacAuthorityLab.exe
```

Запускать Isaac или звать друга для этой проверки не требуется. Python запускает два отдельных процесса, выбирает свободный порт через bind(port=0), передаёт общий идентификатор сессии и сравнивает итоговые состояния. UDP привязан только к `127.0.0.1`; интернет-подключения этот этап не поддерживает.

## Что реализовано

- Хост выполняет собственные шаги независимо от наличия клиентского ввода. При отсутствии команды применяется нейтральный ввод; клиентский персонаж замедляется. Симуляция хоста продолжается.
- Клиент немедленно предсказывает движение. Снимок хоста содержит подтверждённый номер ввода; клиент возвращается к авторитетному состоянию и повторяет ещё не подтверждённые команды.
- Один шаг хоста применяет не более одной команды удалённого игрока. Пакетная доставка не ускоряет игровое время.
- Команды имеют возрастающие номера. Дубликаты и уже обработанные команды отвергаются. Если более ранняя команда не пришла, хост может обработать следующую и подтвердить пропуск; ожидания всех клиентов нет.
- Истории ограничены 256 командами. Если клиент исчерпал историю без подтверждений, предсказание приостанавливается; хост продолжает работу. Стенд повторно отправляет до восьми старейших неподтверждённых команд за шаг.
- Номер комнаты отделяет новые состояния от запоздавших пакетов старой комнаты; `NewRoom` очищает накопленный ввод и предсказание. Доставка состояния комнаты с повторными подтверждениями ещё не реализована.
- Формат пакета задаётся явно, без сериализации сырых структур C++. Проверяются размер, версия, вид, идентификатор сессии, допустимый слот и числовые значения.

## Протокол v1

Фиксированные 72 байта, little-endian; float32 в полезной нагрузке.

| Смещение | Поле |
| --- | --- |
| 0 | Magic `AUTH`, 4 байта |
| 4 | Версия u16=1, вид u16: input=1 / snapshot=2 / hello=3 |
| 8 | Идентификатор сессии u64 |
| 16 | Номер комнаты u32, начиная с 1 |
| 20 | Input: слот 1; snapshot: число игроков 2; hello: 0 |
| 24 | Номер команды input; иначе 0 |
| 28 | Шаг snapshot; иначе 0 |
| 32 | Подтверждённая команда snapshot; иначе 0 |
| 36 | Резерв, 0 |
| 40 | Input: x/y движения, остальное 0; snapshot: x/y позиции и скорости каждого из двух игроков; hello: нули |

Идентификатор сессии защищает от смешивания тестов, **не является сетевой аутентификацией**. Клиент не передаёт позицию: он владеет только вводом своего слота. Хост закрепляет первый endpoint с корректным hello; клиент принимает снимки только от endpoint хоста. Это локальный стенд; для выхода в сеть нужны аутентификация, согласование версии/контента, транспорт и управление участниками.

## Проверки

`authority_invariants` проверяет повреждённые/усечённые/чужие пакеты, NaN, дубликаты, ограничение скорости обработки ввода, старые комнаты, устаревшие снимки, неверные подтверждения, повтор предсказания, переполнение и восстановление истории. Сценарий на 900 шагов включает задержки, перестановку, дублирование, потери и остановку клиента на 180 шагов; после доставки свежего состояния клиент сходится с хостом.

`authority_two_processes` проверяет реальный UDP: 400 шагов хоста, остановка клиентской обработки на 80 интервалов, пропуски ввода и снимков, последующее точное совпадение положения/скорости. Интервал стенда 10 мс выбран для короткого теста и не утверждает частоту симуляции Isaac. Финальная сходимость проверяется после прекращения нового ввода и обработки оставшихся команд; визуальная плавность здесь не измеряется.

Логи проверки находятся в `Binaries/authority-build/Testing/Temporary/LastTest.log`.

## Следующий этап: адаптер J460

Карта исследования: [authority-j460-integration.md](../../docs/authority-j460-integration.md). Проверены источник на игровом потоке, реплика игрока и обычных слёз. Пока не реализованы атомарный снимок мира, управление остальной симуляцией клиента, интерполяция отображения, синхронизация врагов/остальных снарядов/предметов/урона, загрузка комнаты, позднее подключение, переподключение и миграция хоста.

Прямое применение позиции поверх официальной lockstep-сессии не заменит её модель: старый цикл продолжит ожидать ввод и проверять расхождения. Игровой прототип должен получить отдельный путь запуска и управление симуляцией клиента. Подмена существующего диагностического загрузчика этим стендом не выполнялась.
