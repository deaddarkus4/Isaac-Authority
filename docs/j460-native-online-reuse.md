# Смена курса: взять онлайн самой игры и заменить в нём только синхронизацию

**20 сентября 2026.** Предложение пользователя после [процесса лобби](j460-lobby-process.md): не строить рядом с игрой собственные лобби, транспорт и создание игроков, а использовать штатные компоненты — «даже тот же мультиплеер, просто изменить в ключевых функциях логику сети». Документ фиксирует, что для этого уже известно из бинарника J460 (только статический разбор, игра не запускалась) и какой план из этого следует. Результаты Ghidra — `Binaries/research/j460-net-service*`, `j460-lockstep-*` (в git не входят).

## Что решил пользователь

- **Модель доверия.** Авторитет хоста — только над миром: положения, события и тому подобное. Статусы, статы, предметы своего персонажа считает его владелец, остальные ему доверяют; считать это отдельно на хосте «пока муторно».
- **Что болит.** Десинк — худшее; задержка ввода отдельно выводит из себя.
- **Как ведёт себя штатное восстановление** (со слов пользователя, из первых рук): игрока выбрасывает из лобби в собственное лобби — либо вдвоём с кем-то из друзей, то есть компанию может разделить пополам; он остаётся в том же месте с теми же вещами, но без друзей. Это раскол сессии, а не синхронизация, поэтому опираться на него как на «хост всегда прав» нельзя.

Следствие модели доверия: свой персонаж авторитетен у себя, значит **предсказание и сверка своего игрока не нужны**, а задержка ввода исчезает по построению — ввод применяется сразу, хост его не пересчитывает.

## Что найдено в игре

### Сетевой сервис выбирается фабрикой, и локальный сервис в ней есть

Фабрика — RVA `0x629370`, текущий сервис — глобальный указатель RVA `0x879a58`:

| Аргумент | Сервис | Таблица методов (RVA) |
| --- | --- | --- |
| 0 | нет | — |
| 1 | `KAGE::Network::Multiplayer::ServiceLocalhost` | `0x7a23a4`; лобби `LobbyLocalhost` `0x7a8330`, соединение `ConnectionLocalhost` `0x7a839c` |
| 2 | `ServiceSteam` | `0x7a2440` |
| 3 | EOS | `0x7a2530` |

Локальный сервис — полноценный код: при создании разрешает окну сообщение `0x4a` (`WM_COPYDATA`), то есть экземпляры игры на одной машине разговаривают оконными сообщениями, без Steam. **Ни один из девяти вызовов фабрики не передаёт 1**: все выбирают между 2 и 3 по полю платформы `Manager+0x2a3fc`. Похоже на стенд разработчиков, оставленный в релизе; ключ `--localhost_match`, который лишь разводит журналы экземпляров по файлам, по всей видимости сделан для него же *(вывод, не факт)*. Работает ли локальное лобби до конца, неизвестно: в бинарнике есть строка `Localhost lobby values currently not supported`.

Если это заработает, снимается главная причина, по которой проект шёл снаружи игры: штатный онлайн негде было проверять — два экземпляра под одним аккаунтом Steam друг с другом не играют.

### Ядро lockstep

| Что | Где (RVA) | Что делает |
| --- | --- | --- |
| Ворота кадра | `0x510980`, метод сетевого менеджера; текущий кадр — `менеджер+0xc` | обходит все сетевые устройства ввода (`0x501cb0` — «готово ли устройство к этому кадру») и очереди событий, назначенных на кадр; пока хоть одно не готово, возвращает 0 и кадр не считается. **Это и есть ожидание самого медленного и источник задержки ввода** |
| Приём ввода | `NetInputDevice::ProcessInputMessage` `0x502010` | пакет: контрольная сумма (та же затравка `0xFEDCBA76`, что у сохранений), 12 байт заголовка, номер кадра, 16 байт записи ввода; кадры раньше `Manager+0x4b3e4` и уже имеющиеся отбрасываются. `CHECKSUM MISMATCH` здесь — целостность пакета, не состояние игры |
| Есть ли ввод кадра | `0x501190` | вызывается воротами, приёмом и ещё двумя функциями |
| Автомат десинка | `0x4fd900` | `Recovery Start`, `Desync Handler creating new lobby` — тот самый раскол лобби |
| Задержка ввода | `0x524440`, `0x524d10` | чтение и запись настройки `OnlineInputDelay` |
| Уже разобрано раньше | [сохранение лобби](j460-lobby-save.md) | сбор общего сохранения, рассылка при старте, наложение поверх своего, обратная запись |

## План

Штатное остаётся как есть: лобби и его интерфейс, общее сохранение, синхронный старт, создание игроков из состава лобби, сетевые устройства ввода, транспорт. Меняется только синхронизация.

0. **Поднять штатный матч локально.** В двух изолированных экземплярах подставить фабрике аргумент 1, пройти меню Online, посмотреть, создаётся ли лобби и стартует ли матч с двумя игроками. Сервис Steam при этом не создаётся. Это первое вмешательство в код игры и первый вход в пункт Online — **только по слову пользователя**.
1. **Свободный ход.** Убрать ворота кадра и реакцию на расхождение контрольных сумм состояния: каждый экземпляр считает сам, свой ввод применяется сразу. Лобби перестаёт раскалываться.
2. **Чужие игроки — по состоянию владельца.** Обновление чужого игрока удерживается, тело ставится из присланного владельцем (положение, скорость, направление, события: выстрел, бомба, предмет). Это уже умеет наш модуль мира (`playerUpdatesHeld`, секция игроков WLD1).
3. **Мир — по хосту.** Враги, зачистка комнаты, двери, переходы: снимки хоста поверх локального расчёта. Умеет модуль мира для обычных комнат, слёз и врагов.
4. **События, требующие согласия:** подбор предметов, смена этажа, смерть и возрождение — по решению хоста или владельца, по одному.

Канал на первых шагах — наш Python-транспорт через общую память; затем собственный тип сообщения в соединении самой игры.

**Что из сделанного остаётся в деле:** перехваты обновления игрока, слёз, врагов и ввода; WLD1; модель плохой сети; карта памяти; отпечаток уровня и формат сохранений; стенд с изолированными экземплярами. **Что становится запасным путём:** INP1 с воспроизведением по шагам, предсказание и сверка своего игрока, Python-лобби — они нужны, только если локальный сервис не заработает.

## Шаг 0 — что получилось (20 сентября 2026, по слову пользователя)

Модуль `IsaacAuthorityLocalhost.dll` (`native/IsaacAuthority/src/localhost_adapter.cpp`, подключение `IsaacAuthorityAttach localhost <PID> <DLL>`): шесть байт на входе фабрики заменяются переходом на заглушку, которая превращает любой запрос сервиса, кроме «нет», в запрос локального. Это первая правка кода игры в проекте; модуль отказывается работать где-либо, кроме изолированного экземпляра (проверяет подменённое имя папки сохранений), сверяет байты входа и умеет вернуть их обратно. ### Почему зависал старт и как это исправлено

Запуск забега (RVA `0x559720`) в сетевом режиме ждёт функцию RVA `0x50c400`: у **каждого слота игрока** и каждого участника должен найтись его сохранение в словаре сетевого менеджера. Чтение памяти зависших экземпляров показало: слоты игроков названы идентификаторами локального сервиса (дескриптор окна игры, над ним `0xfefefefe`), а своё сохранение каждая игра положила в словарь под **Steam id** — потому что «локальный пользователь» (объект по RVA `0x873674`, id в `+8`) при запущенном Steam несёт Steam id. Для собственного слота сохранения не находилось никогда. У разработчиков стенд, видимо, работал без Steam.

Проверка догадки: принудительный ответ «да» из `0x50c400` дал `Start Networked`, общий seed и создание обоих игроков — и сразу падение в обоих экземплярах (состав собран с неверной личностью). Исправление — в самом модуле: при подключении он даёт локальному пользователю ту личность, под которой игру знает локальный сервис (дескриптор своего окна и `0xfefefefe`; окно берётся из объекта GLFW, RVA `0x87999c` `+0x2b4`, и проверяется, что оно принадлежит этому процессу); при отключении возвращает прежнюю. Steam id нигде не сохраняется и не печатается.

Свежая пара с теми же двумя сохранениями. Хост: Online → Quick Match → «лобби не найдены, создать?» → Create; гость: Online → Quick Match → вошёл; Tab у обоих.

## Шаги 1 и 2 — свой игрок без задержки, чужой по состоянию владельца (20 сентября 2026)

Модуль `IsaacAuthorityNative.dll` (`native/IsaacAuthority/src/native_adapter.cpp`, подключение `IsaacAuthorityAttach native <PID> <DLL>`), только для изолированных экземпляров. Стенд: `scripts/Start-IsaacNativePair.ps1 -Saves <хост>,<гость>` поднимает пару на локальном сервисе; `scripts/Enter-IsaacNativeLobby.py host|guest|ready <PID> intro|title|lobby <лист.png>` проводит игру по штатным меню в лобби — со снимком окна после каждой клавиши, с проверкой перед каждой значимой клавишей (прежде всего — что сетевой сервис `LOCALHOST`) и остановкой при любом несовпадении; `scripts/Test-IsaacNative.py` подключает модуль, гоняет ретранслятор и измеряет.

**Шаг 1.** Перехват чтения ввода (слот 29 менеджера ввода — тот же, что у прежних модулей; в онлайне игра читает игроков по номерам устройств лобби, 2 и 3, теми же тремя читателями). Для своего игрока ответ даёт физическое устройство, сразу; сетевое устройство игры продолжает рассылать остальным ввод по расписанию lockstep. Какой номер свой, стенд берёт из журнала игры (`Adding local player` → `Setting controller ID to N`). Игры перестают считать одинаковые кадры, поэтому сверка контрольных сумм кадров (RVA `0x50d4a0`, при расхождении зовёт автомат десинка `0x4fe3a0` — тот самый раскол лобби) отвечает «равны»: восемь байт на входе, сверяются перед записью.

**Шаг 2.** После своего обновления игрок публикует тело — положение и скорость — в ячейке памяти модуля; после обновления чужого игрока его тело заменяется самым свежим присланным владельцем (сообщение `PLR1`, 28 байт, на loopback-сокет модуля; принимается только более новый номер, только для чужого контроллера, только конечные числа, не старше 250 мс). Всё остальное у чужого игрока по-прежнему считает сама игра из его ввода. Переносит тела пока ретранслятор теста, через `isaac_link.py` можно портить ему сеть.

| | Штатный lockstep | Шаг 1 | Шаги 1 + 2 | 1 + 2, сеть обмена 100 мс + 80 мс дрожания, 15 % потерь |
| --- | --- | --- | --- | --- |
| От клавиши до движения своего игрока | 134–149 мс | 23–27 мс | 19–42 мс | 28–46 мс |
| Отставание копии у соседа в движении, медиана | 0 (все считают одно и то же, но все с задержкой) | 9–43 пикс. | 0–3,8 пикс. | 30–31 пикс. — время пути, 140 мс |
| То же, максимум | 0 | 17–48 | 4,4–8,8 (один-два шага движения) | 40–48 |
| Расхождение копий в покое | 0 | 0–0,32 | 0,000 | 0,000–0,006 |
| Самая большая поправка | — | — | 4,4 пикс. | 17,6 пикс. |
| Лобби | цело | цело, строк о десинке в журналах нет | цело | цело |

Обе игры всё время считают 30 кадров в секунду, отпечаток уровня одинаков. Для сравнения: в одиночной игре от клавиши до движения 15 мс.

**Что вскрылось по дороге.**

- *Общая клавиатура стенда.* У изолированных экземпляров отключена пауза при потере фокуса, и прямое чтение клавиатуры в окне без фокуса видит нажатия, предназначенные другому окну: клавиша в окне B вела и игрока A, его тело уходило соседу, и копия прыгала на 345 пикселей. Свой игрок теперь слушает клавиатуру, только когда окно игры на переднем плане (проверка не чаще раза в миллисекунду). Правило верное и вне стенда.
- *Загруженный модуль нельзя трогать пересобранным файлом.* Остановка старого модуля через новый файл по тому же пути уронила обе игры: адрес экспорта считается по файлу, а в памяти другая сборка. Это старое правило проекта — перезапускать игры перед обновлением модулей; я его нарушил. Пострадали только изолированные экземпляры.
- *Инструмент снимков окна зависает.* Снимки теперь делает собственный помощник с таймаутом: одна клавиша → пауза → снимок только окна игры по его рамке (`DwmGetWindowAttribute`), и только если это окно на переднем плане.

## Шаг 3 — враги принадлежат хосту (20 сентября 2026)

Тот же модуль. Хост — игра, создавшая лобби (стенд узнаёт это по строке `Successfully created lobby` её журнала и пишет в конфигурацию модуля слово `host`).

**Сначала — что будет без авторитета** (шаги 1 + 2, бой в соседней комнате, стреляет игрок хоста): обе игры сами перешли в комнату — переход комнат штатный lockstep делает сам, — и через две секунды боя миры разошлись молча: положения врагов до 39 пикселей врозь, здоровье на 3,5 единицы, а потом один враг умер у гостя, но остался жив у хоста. Раскола лобби нет, но это и есть десинк, только без симптомов.

**Как сделано.** Раз в кадр хост публикует живых врагов своей комнаты — seed, тип, вариант, положение, скорость, здоровье — и seed тех, кто недавно умер (сообщение `WLN1`, 1620 байт, до 48 врагов и 16 смертей). Каждая игра по-прежнему считает своих врагов сама, гость накладывает состояние хоста поверх:

1. сопоставление по seed — комнату обе игры генерируют одинаково, поэтому seed совпадают;
2. враг, родившийся посреди боя, получает seed из случайного потока, который у сторон уже разный, — такие сопоставляются по типу, варианту и близости, пара запоминается;
3. умерший у хоста убивается у гостя штатной функцией, которую зовёт Lua-метод `Kill()` (RVA `0x45dc30`);
4. местный враг, которому у хоста нет пары двадцать снимков подряд, удаляется;
5. **гость сам врага не убивает:** смертельный удар в его собственной симуляции (`Entity_NPC::TakeDamage`, слот 8 таблицы, RVA `0x2d60a0`) срезается до несмертельного, смерть приходит только от хоста. Без этого гость терял врага из виду раньше хоста и навсегда.

Снимок чужой комнаты не применяется; то же добавлено телам игроков — у двери игры меняют комнату с разницей в кадры.

| Бой в соседней комнате | Без авторитета (шаги 1 + 2) | С врагами от хоста |
| --- | --- | --- |
| Положения врагов у сторон | до 39 пикс. врозь, растёт | 0–2 пикс. весь бой, поправка в среднем 0,3 пикс., наибольшая 6,7 |
| Здоровье врагов | расходится на 3,5 | равно; гость поправил 14 раз |
| Смерти | враг умер у гостя и жив у хоста | 3 из 3 пришли от хоста; 3 смертельных удара на госте срезаны |
| Конец боя | составы разные | комната зачищена у обоих одновременно, игроки совпадают до сотых |

В одном из прогонов, до пунктов 2 и 4, враги-пауки, родившиеся в бою, остались у гостя четырьмя «сиротами» при пустой комнате у хоста — отсюда эти пункты. Комнаты с рождающимися врагами после правки под рукой не оказалось: сопоставление по близости и удаление сирот **собраны, но живьём не сработали ни разу** (счётчики `npcPaired`, `npcRemoved` остались нулевыми).

**Чего ещё нет.** Выстрелы, бомбы и предметы своего персонажа у соседей по-прежнему происходят по расписанию lockstep и из слегка другой точки: урон врагам у гостя косметический (его перекрывает хост), но урон *игрокам*, подбор предметов, двери и смена этажа пока считает каждая игра сама — это шаг 4, события по одному. Если хост не умеет создать у гостя врага, которого у гостя нет (`npcOnlyHost`), — он там просто не виден; нужна функция создания сущности. Ворота кадра lockstep на месте: при настоящей сетевой задержке игра по-прежнему ждёт ввода самого медленного. Транспорт — ретранслятор теста, а не соединение игры. Отставание копии при задержке сети можно убрать экстраполяцией по скорости — не сделано.

## Шаг 4, первое событие — урон игроку (20 сентября 2026, проба пользователя)

Пользователь сам сыграл в локальном матче (`Test-IsaacNative.py --play`: модули и ретранслятор работают, тест клавиш не нажимает) и первым же расхождением прислал снимок двух окон: у владельца (хост) 2,5 сердца, у гостя его копия показывает 1,5. Остальное совпало — монеты, бомбы, ключи, карта, смерть второго игрока. Причина ожидаемая: вражеские снаряды и касания у сторон стоят чуть по-разному, и копия получила удар, которого владелец не видел.

Поля найдены чтением памяти обоих игроков в обеих играх в момент расхождения и подтверждены геттерами самой игры (привязки Lua): контейнеры `+0x1340`, красные `+0x1344` (5 против 3), вечные `+0x1348`, синие `+0x134c`, маска чёрных `+0x1350`, костяные `+0x1d88`, гнилые `+0x1da4`, золотые `+0x194c`; призрак кооператива — байт `+0x20a9` (`IsCoopGhost`); штатный флаг «мёртв» `+0x173` у призрака не выставлен.

Сделано по модели пользователя — персонаж принадлежит владельцу:

- сердца владельца едут вместе с его телом (`PLR1` вырос до 76 байт), копия берёт их как есть;
- удар по чужой копии локально игнорируется (`Entity_Player::TakeDamage`, слот 8 таблицы, RVA `0x3729d0`);
- когда владелец стал призраком, а копия нет, копия получает удар, который не пережить, **штатной функцией урона** — чтобы отработала штатная смерть; повтор не чаще раза в 30 кадров.

Проба пользователя после правки: «подстроилось». В журнале ретранслятора за первые полторы минуты: по 4 поправки здоровья с каждой стороны, проигнорировано 116 и 52 удара по копиям (счётчик считает каждый вызов, в том числе отклоняемые самой игрой в кадры неуязвимости), врагов по смерти у хоста убито 6, смертельных ударов на госте срезано 2, и впервые живьём сработало сопоставление рождённого в бою врага по близости (1). Была одна поправка тела на 268 пикселей — при входе в комнату, когда владелец уже отошёл от двери; это не телепорт посреди комнаты, но сгладить стоит.

**Не сделано:** оживление призрака у автомата Revive на копию не переносится (считается счётчиком `copyRevivalsMissed`); у гостя суммарно 110 снимков, в которых у хоста был враг без пары у гостя, — создавать недостающего врага модуль не умеет; смерть копии живьём ещё не наблюдалась.

## Шаг 4, дальше — по расхождениям, которые находит пользователь (20 сентября 2026)

Порядок работы: пользователь играет в двух окнах, присылает снимок расхождения, в модуль добавляется одно правило, пара перезапускается. Общее правило он сформулировал сам по ходу: **«не считать, у кого сильнее, а блокировать у других и синхронизировать с хостом»** — мир принадлежит хосту, персонаж — владельцу.

| Расхождение | Правило | Штатное, что используется | Проверено живьём |
|---|---|---|---|
| Игроки оказались в разных комнатах (после выхода из комнаты сделки) | тело несёт комнату и «эпоху» смен комнаты; кто услышал более новую — идёт следом, при равных гость идёт за хостом | `Game::StartRoomTransition`, RVA `0x2fd7c0` | **нет**: за все сессии переход ни разу не понадобился (`rooms followed 0`) |
| У босса разные атаки; у одного врагов больше | хост шлёт поля поведения врага (`State +0xb64`, `StateFrame +0x410`, `ProjectileCooldown +0xba0`, `V1/V2 +0xbb0/+0xbb8`, `I1/I2 +0xbc0/+0xbc4`, цель `+0x334`); врага, которого у гостя нет 10 снимков, гость создаёт под seed хоста | `Game::Spawn`, RVA `0x28b20` | да: создано 7, отказов 0 |
| Гость зачистил комнату раньше хоста | зачистка гостя удерживается, пока комната хоста не зачищена (бит 0 флагов описателя комнаты, `+0x44`); потом выполняется та же функция | `Room::TriggerClear`, RVA `0x4068f0` (не виртуальная: первые 6 байт заменены переходом) | да: `clears from host 4` |
| Копия умирала на секунду-две позже владельца | владелец шлёт не только «призрак», но и «умирает» — штатный флаг `IsDead`, `+0x173`, выставленный на время анимации смерти; копию, которая ещё умирает, когда владелец ожил, поднимает штатная функция | `Entity_Player::TakeDamage`, `Revive` (RVA `0x3a2220`) | смерть — да (одна попытка вместо четырёх); `Revive` — нет |
| Сундук открыл один, второй «не в курсе» | подбор — событие владельца: касание копии ничего не делает, своя игра сообщает о касании, изменившем предмет (вид, seed, цена, исчез), чужая выполняет то же касание для копии над двойником предмета (по seed, иначе ближайший того же вида в 120 px); последние 8 подборов едут в каждом теле под номерами | столкновение `Entity_Pickup`, слот 23 таблицы `0x767f24`, RVA `0x2e8ae0` | да: взято 4, применено 4 из 4, 15 касаний копий отклонено |
| Враги у гостя не атакуют | вместе с состоянием едет имя анимации врага; у гостя другая — запускается хостовая. Причина: анимацию атаки враг запускает сам при своём переходе, выстрел — событие анимации, а хост всегда на кадр-два впереди и переход «перехватывал» | `ANM2::Play`, RVA `0xa380`; спрайт сущности `+0x48`, текущая анимация `+0x34` от спрайта, начинается с имени | да: `animations started` 15, 5, 4 за боевые интервалы, сбоев 0 |
| Камень разрушен у одного; какашки ломаются в разное время | по правилу пользователя: разрушение у гостя удерживается (пока хост слышен и в той же комнате), хост шлёт ячейки, которые уже не как построены, гость доламывает штатно; недобитым какашкам и TNT ставится состояние хоста. Причина расхождения какашек — случайная прибавка к урону в их `Hurt` | сетка `Room+0x24` (448 ячеек; тип `+4`, вариант `+8`, состояние `+0xc`, спрайт `+0x40`); `Hurt`/`Destroy` — слоты 4 и 5 таблиц камня `0x768738`, какашки `0x768648`, TNT `0x769300`, паутины `0x769558`; обёртка `Destroy` RVA `0x45de20` | да: удержано 5, поставлено с хоста 5, несовпадений 0 |
| Костры расходятся | костёр (тип 33) не умирает от выстрелов, а гаснет при здоровье ≤ 1, поэтому срезанный «смертельный» удар гостя гасил его раньше хоста; удары гостя по костру не действуют, костёр едет с врагами хоста | — | **нет** (собрано, пользователь ушёл на перерыв) |

### Ошибка, которую стоит помнить

Смещение спрайта сущности было взято от функции `GetSprite` **не того класса** (`+0x40` — это `GridEntity`, у `Entity` спрайт по `+0x48`) и не проверено по живой памяти. У хоста чтение имени анимации падало на каждом кадре с врагами (10134 сбоя из 13160 кадров), защита от сбоев глотала исключение, а счётчик записи оставался чётным — гостю уходил мир-обрубок из одного врага с мусорной позицией, остальных гость удалял как лишних. Пользователь увидел это как «враги сами куда-то пропали». Исправлено и закрыто с трёх сторон: смещения теперь сначала читаются в живой памяти обеих игр (`sprite_probe.py`, `grid_probe.py` — имена анимаций и состояния ячеек читаются как есть); перед записью счётчик слота не увеличивается, а делается нечётным (`|= 1`), так что сорванная запись не выглядит целой; число сбоев (`FAULTS`) стоит первым в строке журнала `--play`.

### Что открыто после этих проб

- Снаряды врагов и слёзы игроков — см. следующий раздел: собрано, живьём не проверено.
- Анимации врагов у гостя отстают на кадр-три (столько идёт снимок) — на снимке двух окон это видно, в игре нет.
- Содержимое сундука и награда за зачистку бросаются у каждой стороны своим случайным числом; нужен список подбираемых предметов комнаты от хоста.
- Двери секретных комнат, блоки под ключ, мостики через ямы, автоматы и попрошайки — не покрыты.
- Порог здоровья есть не только у костра: у боссов с фазами локальный урон гостя может на кадр-два раньше перевести фазу (состояние затем вернёт хост).

## Снаряды врагов и слёзы игроков (20 сентября 2026; собрано во время перерыва, **живьём не проверено**)

Пользователь увидел: у босса в отдельные кадры залп есть у одного и нет у другого; случайный эффект слезы сработал у владельца и не сработал у копии. Причина одна — каждая игра бросает это сама. Правило то же: снаряды врагов — мир хоста, слёзы игрока — его владельца.

- Хост кладёт в мир живые снаряды (`Entity_Projectile`, таблица `0x764990`, до 64). Каждая игра шлёт живые слёзы **своего** игрока (`Entity_Tear`, таблица `0x764eac`, создатель `+0x3c8` — свой игрок, до 32) отдельным пакетом `SHT1`; ретранслятор читает третий слот `publishedShots`.
- Получатель держит у себя **ровно этот список**: свой выстрел с тем же seed получает место, полёт, размер, урон, флаги и цвет владельца; которого нет — создаётся штатным `Game::Spawn` под seed владельца (слеза — с создателем-копией); выстрел собственной выделки, которого нет ни в одном списке, удаляется штатным `Remove` (слот 10 таблицы сущности); выстрел, которого у владельца больше нет, умирает как от штатного `Die()` (флаг `+0x173`). Seed, однажды принесённый списком, запоминается (кольцо на 256): если такой выстрел здесь кончился раньше, он не создаётся заново.
- Пока владелец шлёт слёзы, копия не стреляет сама: задержка выстрела её оружия держится поднятой (игрок `+0x13dc`, иначе `+0x13e0`; в оружии `+0xc`). Если владелец слёз не шлёт (лазер, нож), копия стреляет сама, как раньше.
- Поля — по геттерам и сеттерам самой игры из привязок Lua соответствующего класса: высота `+0x410`, скорость падения `+0x414`, ускорение `+0x418`; снаряд — урон `+0x41c`, размер `+0x420`, флаги `+0x438` (64 бита); слеза — размер `+0x424` через её же сеттер (RVA `0x276120`), флаги `+0x428` (128 бит), урон — `CollisionDamage` сущности `+0x388`; цвет — цвет спрайта, `+0xf0`, 44 байта.
- Защита от чужой раскладки: пакет с выстрелом вне разумных границ (высота, скорости, размер, урон, цвет) отвергается целиком и считается в `FAULTS`; слёзы, у которых создатель не свой игрок, не шлются вовсе — при неверном смещении создателя механизм просто молчит (`tears sent 0`).
- Перед первой живой пробой: `shots_probe.py` (только чтение) — слёзы, снаряды и оружие игроков обеих игр с этими полями; разумные значения: высота отрицательная, размер около 1, создатель — один из игроков.

Не входит: слёзы спутников, лазеры, ножи, бомбы — по-прежнему у каждой игры свои; в комнате с более чем 64 снарядами список хоста неполон. Транспорт остаётся прототипным: мир вырос до ~12,8 КБ на кадр, слёзы — 3,5 КБ на игрока; при переносе в соединение самой игры нужны дельты.

## Комната «в покое» от хоста и выключатели правил (20 сентября 2026; собрано без запуска игр, **живьём не проверено**)

По карте из [j460-world-replication-map.md](j460-world-replication-map.md), пока пользователь занят. Всё — тем же приёмом «держать ровно список хоста», что и выстрелы.

- **Подбираемое.** Хост кладёт в мир живые подбираемые предметы (до 64: seed, вид, место, цена `+0x534`, кадров до исчезновения `+0x540`, группа «выбери одно» `+0x528`, слот магазина `+0x53c`). Гость: своему с тем же seed ставит место, цену, таймер и группу; которого у него никогда не было — создаёт штатным `Spawn` под seed хоста (**кроме подтипа 0** — он просит игру бросить случайный: пустой пьедестал и открытый сундук гость не создаёт, считает `skipped`); предмет собственной выделки убирает через 6 снимков; которого у хоста больше нет — через 20, чтобы сначала отработало событие «взял» владельца; пьедестал с другим предметом, чем у хоста, через 15 снимков получает предмет хоста штатным `Entity_Pickup::Morph` (RVA `0x2e30a0`, с сохранением цены и seed). Список, который не поместился, ничего не удаляет.
- **Монеты, бомбы, ключи** — числа хоста на всех игроках гостя, кроме 45 кадров после того, как они изменились у гостя сами.
- **Двери** — ячейки сетки типа 16 класса `GridEntity_Door` (таблица `0x768698`): вариант `+8`, состояние `+0xc`, «взорвана» `+0x391` (смещение из геттера J460; у REPENTOGON для J273 макет двери другой). Дверь, которая 4 снимка подряд отличается от двери хоста и не менялась у гостя последние 30 кадров, получает три значения хоста и штатное обновление двери (RVA `0x30ee40`) — ровно так заканчиваются штатные `Close`, `Bar` и `SetLocked`. Состояния «в пути» (не 1–4) не применяются.
- **Ловушки** из `Room::IsPersistentRoomEntity` едут в списке врагов хоста при любом максимуме здоровья.
- **Бомбы, которые поставил не игрок** (тролли, бомбы врагов), — мир хоста: тот же «ровно список», до 16 штук в мире.
- **Автоматы и попрошайки** (`Entity_Slot`, таблица `0x764c50`). Поля прочитаны в идущей игре пользователя, когда он играл у автоматов: состояние `+0x410` — 1 ждёт, 2 играет; 16 бит `+0x41c` отсчитывают игру с 30 до 0, в нуле игра бросает выплату; счётчик касания `+0x42a` растёт, пока игрок упирается. Пожертвование попрошайке (battery bum, `6.13`) подняло `+0x420` с 0 до 1 при состоянии 1; сломанный взрывом автомат — состояние 3, только что созданный — 0. Приз `+0x414` и таймер `+0x424` в выборках были нулями — не проверены. Хост шлёт до 8 автоматов (состояние, приз `+0x414`, отсчёт, пожертвования `+0x420`, таймер `+0x424`, имя анимации); гость пишет их в двойника, запускает анимацию хоста и **держит отсчёт играющего двойника не ниже 2**, чтобы тот никогда не бросил свою выплату — выплата приходит списком предметов хоста. Касание — событие владельца, как подбор: касание копии нигде ничего не делает (копия, ведомая по пути владельца, стоит вплотную, но не внутри автомата), своё касание ждущего автомата гость у себя не играет, а шлёт (в том же кольце, что подборы, с пометкой; не чаще раза в 8 кадров), и хост играет его штатным столкновением автомата (слот 23, RVA `0x2627e0`) для своей копии этого игрока — платит она из общих счётчиков, которые и так хостовые. Автомат, которого у гостя нет 10 снимков, создаётся штатным `Spawn`. **Исключение — машины с платой здоровьем** (варианты 2 донорская, 5 дьявольский попрошайка, 15 hell game, 17 исповедальня): их столкновение бьёт игрока штатным уроном и играет независимо от результата, а удар по копии нигде не считается — поэтому такое касание гость играет и у себя (платит своим здоровьем), а исход остаётся хостовым. Сломанная машина (в том числе «досданная» до поломки) — просто состояние 3 с хоста; её обломки и выпавшее приходят списком предметов.
- **Факт урона красным сердцам.** Байт комнаты `+0x120c` (в идущей игре пользователя поднимался посреди боя) питает шанс сделки. Хост игнорирует удары по копиям и думал бы, что урона никто не получал, поэтому каждое тело несёт байт своей игры: хост поднимает свой, когда поднят у гостя, гости — по миру хоста. Опускает его только сама игра.
- **Бомбы игрока — владельца**, как слёзы, и едут за ними в том же пакете `SHT1` (класс `Entity_Bomb`, таблица `0x7670f4`, создатель — свой игрок; бомбы Dr. Fetus тоже): место, кадры до взрыва (`+0x410` и двойник `+0x414`, как пишет штатный `SetExplosionCountdown`), урон `+0x418`, флаги `+0x438` (128 бит; штатный сеттер ещё поднимает байт `+0x463` — перезагрузить костюмы бомбы), радиус `+0x44c`. Бомбу, поставленную копией самостоятельно, получатель убирает; бомба, которой у владельца уже нет, взрывается у получателя сразу (таймер 0), а не исчезает — именно взрыв копии у хоста ломает камни и двери мира.
- **Неполные списки.** Хост теперь шлёт, сколько врагов и подбираемого было на самом деле; если в список вошло не всё (больше 48 врагов, 64 предметов, 64 снарядов, 32 слёз), гость по такому списку никого не удаляет и не хоронит, а хост никого не объявляет умершим. Раньше переполненный список врагов убил бы у гостя «лишних».
- **Выключатели.** Третье слово конфигурации модуля — маска правил: `follow, behaviour, clear, taken, grid, fire, projectiles, tears, drops, counters, doors, traps, bombs, hurt, slots`. `Test-IsaacNative.py --without drops,doors` запускает без них, `--restart` сначала останавливает модуль в играх (та же сборка — это безопасно), так что сомнительное правило снимается посреди живой пробы без пересборки и перезапуска игр.

Перед первой пробой: `drops_probe.py` (только чтение) — цены, таймеры, группы, двери (класс, вариант, состояние, «взорвана»), счётчики на обоих игроках, ловушки и их здоровье.

## Первая живая проба пары со всеми правилами (20 сентября 2026, вечер; играл пользователь)

Рядом с ретранслятором работал детектор расхождений; правила, собранные вслепую днём, включены все сразу.

**Заработало с первого раза, без сбоев (`FAULTS 0`):** слёзы владельца (за заход гость создал 3853 двойника штатным `Spawn`, погасил 815, убрал 981 собственную слезу копии; выстрел копии удерживается), снаряды врагов (63–229 создано, столько же своих убрано), бомбы игроков и врагов, список подбираемого (17 создано, 10 убрано), общие счётчики (5 поправок), двери (1 поправка), факт урона красным сердцам (хост узнал 7 раз), сетка, зачистка, подбор. Детектор за второй заход назвал 38 устойчивых расхождений — **все одного вида** (см. ниже), то есть остального он не видел расходящимся.

**Падение гостя при входе к составному боссу** (сущность типа 881, сегменты связаны указателями родитель/потомок `Entity+0x3bc/+0x3c0`). Правило «врага, которого у гостя нет, создать; лишнего удалить» создавало сегменты голым `Spawn` — без родителя, которого им даёт собственный код игры, — и удаляло другие; у гостя к этому моменту было «создано 32, удалено 15». Дамп игра записать не успела, причина — по журналу игры (`Caught exception` сразу после `Spawn Entity with Type(881)`) и счётчикам. **Исправлено:** часть чего-то (есть родитель или потомок) списками не создаётся и не удаляется; место, здоровье, поведение и смерть по-прежнему от хоста. Счётчик `parts of enemies left alone`.

**Питомцы** (слова пользователя: «всё, что касается игрока, — только для петов»): фамильяр `3.58` с одним seed стоял у сторон в разных местах. Фамильяры — владельца: `Entity_Familiar` (таблица `0x76491c`), игрок `+0x410`, задержка выстрела `+0xd4c` (геттеры J460). Каждая игра шлёт фамильяров своего игрока в пакете слёз (до 24: seed, вид, место, скорость), фамильяры копии встают на них — по seed, иначе по порядку среди своего вида. Слёзы фамильяра считаются слезами его игрока (условие «чьё это» расширено: создатель — сам игрок или его фамильяр), а пока слёзы приходят, фамильяры копии не стреляют. Живьём после правки счётчики питомцев ещё не смотрел. Лазеры и ножи питомцев — по-прежнему у каждой игры свои.

**Ячейки сетки, которые рождаются в бою.** Босс, сыплющий какашками, бросает клетки в каждой игре сам: у хоста 12 какашек в одних клетках, у гостя 12 в других, а состояние ячейки, которой у гостя нет, поставить нельзя (`mismatch 457`). Теперь мир несёт карту ломаемых ячеек хоста (448 бит) и ячейки, родившиеся с момента входа хоста в комнату (индекс, тип, вариант, seed); гость создаёт недостающую штатным `Room::SpawnGridEntity` (RVA `0x3ebca0`) и через 10 снимков убирает ломаемую ячейку, которой нет на карте хоста, штатным `Room::RemoveGridEntity` (RVA `0x41e930`; только ставит удаление в очередь).

**«Сетевой троттлинг» на одной машине.** Пользователь чувствует лёгкие заикания и на хосте, и на копии. Замер снаружи (опрос счётчика кадров, `frame_pacing.py`): 5–7 % кадров длиннее 45 мс — **одинаково с ретранслятором и без него, с детектором и без**, то есть обмен модуля ни при чём; подозреваемый — штатный покадровый lockstep (кадр ждёт ввод соседа). Попытка: `OnlineInputDelay=5` в настройках тестовых профилей (значение читается в `0x524440`, по умолчанию 3, обрезается до 1…5; свой игрок у нас читает клавиатуру напрямую и задержки не чувствует) — внешний замер разницы не показал, но сам замер оказался груб: длинные и короткие интервалы идут парами поровну, что характерно для погрешности опроса (±15 мс), а не для заиканий. Поэтому счётчик интервалов кадра встроен в модуль (`frames over 45 ms` в строке журнала) — вывод отложен до него. Заодно копия теперь ставится с упреждением на возраст пакета (место + скорость × возраст в кадрах, не больше 2): кадры двух игр идут не в ногу, и копия, поставленная ровно туда, где владелец был, дёргается на долю кадра. Пользователь: «хуже, будто скользит… а нет, норм вроде». Отключается правилом `lead`.

## Свой обмен модулей и сборка для пробы между Steam-клиентами (20 сентября 2026, поздний вечер)

До сих пор состояние между играми носил Python-стенд (читал опубликованные слоты из памяти одной игры и клал в другую). Теперь модули шлют друг другу сами, и стенд в обмене не участвует (`Test-IsaacNative.py` по умолчанию; прежний путь — `--carried`, он нужен для задержки, дрожания и потерь).

- **Кадр.** Заголовок 16 байт (`IAF1`, вид: тело / выстрелы / мир, номер куска, число кусков, номер кадра, полный размер) и куски не больше 1184 байт (*с 0.1.3, протокол 4: заголовок 20 байт — добавлен номер старта отправителя, куски до 1180; см. «Ревью кода обмена»*); мир и выстрелы пакуются — в путь идут только занятые записи списков. Сборка по соседям раздельно; кадр, у которого потерян кусок, выбрасывается целиком (`frames lost in pieces`). Принимается только от адресов, названных в конфигурации.
- **UDP** (`listen=ПОРТ peer=IP:ПОРТ` в конфигурации) — локальная пара и любые две машины с открытым портом. **Проверено живьём, играл пользователь:** `FAULTS 0`, потерянных кадров 0, детектор расхождений за 9 минут (541 проверка) не назвал ни одного расхождения дольше 3 с; «по плавности вроде хорошо».
- **Steam** (`steam steampeer=ID64…`). Модуль ничего своего не грузит: берёт у уже загруженной игрой `steam_api.dll` четыре плоских экспорта `ISteamNetworkingMessages` (`SteamAPI_SteamNetworkingMessages_SteamAPI_v002`, `…_SendMessageToUser`, `…_ReceiveMessagesOnChannel`, `SteamAPI_SteamNetworkingMessage_t_Release`; в DLL игры проверены по именам, интерфейс `SteamNetworkingMessages002`) и шлёт те же кадры соседу по Steam id через канал 7460, ненадёжно, без Nagle, с самовосстановлением сессии. Отправка пользователю сама принимает его сессию, поэтому обратные вызовы не нужны; NAT и порты — забота Steam. **Живьём не проверено и в одиночку не проверяется: нужны два аккаунта.**
- **Рукопожатие: пока модуль есть не у всех, игра остаётся штатной до последнего байта** (кадр `HEL1`, вид 4: протокол, правила, стадия). Стартовавший модуль только «здесь»: перехваты стоят, но пропускают всё насквозь, **сверка контрольных сумм не тронута**, наружу идут лишь два hello в секунду. Когда hello того же протокола пришло от **каждого** другого игрока матча — модуль выключает сверку (на потоке игры, из перехвата обновления игрока: в этот момент поток игры не может быть внутри патчимой функции) и сообщает об этом; когда то же сказали все — становится активным (`Live()`): ввод с клавиатуры, удержания, правила. Никто не расходится, пока хоть один сосед ещё сверяет. Если за 60 с ответили не все — модуль сдаётся, снимает перехваты и больше ничего не шлёт. **Проверено живьём на паре:** модуль разрешён одной игре из двух — сверка у обеих штатная, уровни равны, через минуту перехваты сняты; разрешён обеим — `LIVE` у обеих через секунды, `FAULTS 0`.
- **Мир и выстрелы уходят на каждом втором обновлении игрока** (30 раз в секунду — с частотой кадров мира), тело — на каждом. Поток хоста в пустой комнате 39 → 30,5 КБ/с, у гостя 23 КБ/с; большую часть составляет тело (360 байт 60 раз в секунду, из них 256 — восемь записей о подборе, обычно пустых) — есть что ужать.
- **Номера устройств растут от матча к матчу** (в настоящем журнале пользователя встретились 12, 13, 14) — таблицы по контроллеру расширены до 64. Строки «Successfully created lobby» под Steam в журнале нет, поэтому **хост — игрок с наименьшим номером устройства**: все клиенты нумеруют игроков одинаково и сходятся на нём без переговоров. *Это допущение по журналу одного матча, до первой пробы не подтверждено.*

**Установка вместо запуска** (по слову пользователя: «не Start/Stop, а Install/Uninstall»). Рядом с `isaac-ng.exe` кладутся два файла, файлы игры не меняются:

- `version.dll` (`native/IsaacAuthority/src/version_proxy.cpp`) — загрузчик. `VERSION.dll` статически импортирует `EOSSDK-Win32-Shipping.dll` игры, а Windows ищет её сначала в папке игры (своей `version.dll` у игры нет; `dbghelp.dll`, наоборот, у игры своя — её имя занимать нельзя). Все 17 экспортов — прыжки в системную `version.dll`, загруженную по полному пути; в процессе `isaac-ng.exe` (и только в нём: рядом лежит `crash_uploader.exe`) отдельным потоком грузится `IsaacAuthorityNative.dll` и вызывается `IsaacAuthorityNativeAuto`.
- **Модуль сам ведёт себя от матча к матчу** (`Supervise`): четыре раза в секунду дочитывает журнал игры (`<Документы>\My Games\<папка сохранений из образа игры>\log.txt`; тот же путь игра пишет в `savedatapath.txt`). `Start Networked` открывает матч; `Adding local player` → `Setting controller ID to N, (Prev: 0)` — своё устройство; `Adding remote player, UserID = …, device ID = N` — соседи; `Menu Game Init` / `Leaving current lobby` закрывают матч; `Input device (ID = N) disconnected` — игрок ушёл. Через 1,5 с после последней такой строки модуль стартует сам: хост — наименьший номер устройства, соседи — по Steam id (принимаются только id людей, `0x01100001…`). Конец матча или сдавшееся рукопожатие — модуль снимает перехваты и **возвращает сверку**. Ушёл игрок, другие остались — перезапуск с новым составом (хостом становится следующий по номеру, сверка остаётся выключенной); остался один — модуль выключается, игра идёт дальше.

Ревью `native_adapter.cpp` чтением кода, без запуска игр. Исправлено то, что не требует живой пробы; **протокол 4, версия 0.1.3** (со сборками 0.1.0–0.1.2 не включится: у них `hellos of another version`, у нас то же).

До этого у выпускаемого модуля не было ни одного теста.

Теперь на каждом снимке из них уходит тот, кого уже нет (у хоста — для `missing`, у себя — для остальных); при неполном списке сторона не чистится.
- **Рукопожатие сверяет `host` и `rules` из hello** (раньше поля шли, но не читались): дальше «здесь» модули идут, только если хост среди них ровно один и маски правил равны. Иначе — ожидание и через 60 с отказ с причиной в заголовке окна и в `.status` (`NOT AGREED: …`). Два хоста или ни одного при выключенной сверке означали бы тихое расхождение: мир не применяет никто. Отказ не мгновенный намеренно: при уходе игрока соседи перезапускаются с разницей в доли секунды, и hello старого старта может временно «не сходиться».
- **Номер старта (session) в каждом кадре.** Модуль считает `sequence` с единицы при каждом старте; сосед, не перезапустившийся вместе с ним, отбрасывал всё последующее как устаревшее — до конца матча. Теперь заголовок несёт номер старта отправителя (часы в десятых секунды, всегда больше прошлого); получатель, увидев более новый, забывает достигнутые номера, недособранные кадры и стадию этого соседа, а счёт подборов и попаданий копии начинается заново. Кадр более старого старта — отставший, кроме случая, когда известный старт молчит дольше 3 с (часы переведены назад).
- **FAULTS больше не смешивает сбой в игре и сетевой мусор.** `gameFaults` — исключения на потоке игры (это и есть `faults` в `.status` и `FAULTS` в стенде), `rejected` — отброшенные датаграммы (`datagrams refused`). Модуль помнит, какое правило работало в момент сбоя; **третий сбой одного правила выключает его в этой игре до конца матча** (`faultRules`, в `.status` — маска в hex): правило с неверным смещением падало бы на каждом кадре внутри кода игры. В hello по-прежнему идёт настроенная маска.
- **Лишний враг гостя уходит `Remove` (слот 10), а не `Kill`:** его у хоста не было, он не умирал — без крови, половинок делящегося врага и выпадений. Прочитано в EXE (SHA256 J460 совпал): слот 10 таблицы врага — `0x2b8f00`, смотрит один тип (866) и хвостом переходит в базовый `Entity::Remove` `0x2acb00`, без аргументов. Умершие у хоста по-прежнему умирают `Kill`.
- Попутно: поздний дубль куска уже собранного кадра больше не засчитывает следующий кадр «потерянным».

**Найдено и НЕ исправлено — нужна живая проба или решение пользователя:**

1. **Идентичность игрока — номер контроллера.** Двое на одном контроллере (Jacob и Esau и подобные, если доступны в онлайне — *не проверено*): ветка своего игрока срабатывает дважды за кадр (`frame` идёт вдвое быстрее, тело публикуется попеременно от двух сущностей), обе копии у соседа берут одно тело. В прежнем пути это уже было выучено («идентичность — место в списке»).
2. **Только клавиатура.** `OnInput` читает устройство 0, разбор журнала берёт своё устройство только из строки с `(Prev: 0)`. У игрока с геймпадом (*предположение по коду*) модуль не стартует, остальные ждут 60 с и сдаются; в README об этом нет.
3. **Урон гостя по врагам — не событие:** засчитывается, только если копия слезы на хосте сама столкнётся с врагом хоста; слезе, кончившейся у владельца, ставится `dead` без урона. Положения врага у сторон разнесены на два времени пути — при реальном пинге попадания по подвижным врагам должны теряться (*вывод из кода, не замерено*). По модели «выстрелы — владельца» попадание должно быть событием владельца (seed врага, урон).
4. **Код игры правится не с потока игры:** возврат сверки в `End` и 6 байт `TriggerClear` пишутся из `Supervise`, хотя выключение сверки намеренно сделано на потоке игры; `Begin` сбрасывает общее состояние без `inboxLock`, не дожидаясь выхода потока игры из перехвата. Окно мало (перезапуск посреди боя), цена — падение.
5. **Данные соседа без диапазонов:** `body.health`, `room`/`dimension` для `StartRoomTransition` (защита — только SEH), `type`/`variant` для `Spawn`, NaN в `target`/`v1`/`v2` врага.
6. **Подбор без страховки по состоянию:** пустой пьедестал или открытый сундук у хоста при полном у гостя не сводятся (`ApplyDrops` меняет предмет только при двух ненулевых subtype) — возможен дубль предмета. Следования на другой этаж по-прежнему нет.
7. Мелочи: страница трамплина `TriggerClear` остаётся после каждого матча; при одном соседе принимается любой отправитель Steam (матч на троих показал, что смещение id верное — обход не нужен); направление в `FollowRoom` для больших комнат всегда −1; после 64-го номера устройства `Begin` откажет.

**Три находки пользователя в магазине — причины найдены чтением памяти обеих игр и разбором функций игры, исправлены, собраны (12/12 CTest), живьём ЕЩЁ НЕ проверены:**

1. **Потухший костёр ранит гостя, монета «под спрайтом».** Посылка правила 0.1.2 неверна: у потухшего костра **на хосте** `CollisionDamage` остаётся 1.0. Игра при затухании меняет другое: `GridCollisionClass` (`+0x184`) и `EntityCollisionClass` (`+0x188`) → 0 и `RenderZOffset` (`+0x354`) → −1000 (сравнение сущности хоста с близнецом гостя: у гостя 3, 4 и 0; смещения — по штатным функциям доступа J460, простые записи). Близнец гостя сам не гаснет — состояние ему пишется, — поэтому продолжал ранить, а угли рисовались поверх выпавшей монеты. Теперь эти три поля идут в списке врагов хоста (`Npc` 112 → 124 байта), гость пишет их вместе с поведением; диапазоны проверяются.
2. **Автомат пожертвований: табло и счётчик только у хоста.** По разбору `Entity_Slot::Update` (`0x25d950`) пожертвование совершается в кадр, когда доигрывает анимация монеты: счётчик сохранения №20 (`FUN_00929b40(0x14,1)`; у жадного автомата — №0x73 и личные счётчики персонажей), цифры табло, достижения 10…999 монет, заклинивание из RNG автомата. У гостя анимация не доигрывала никогда: хост на кадр-два впереди, и его следующая анимация перезапускала близнеца. **Гость не получал в сохранение ни счётчика, ни достижений.** По слову пользователя в штатной игре пожертвование проигрывается у каждого — теперь так и сделано: автоматы вариантов 8 и 11 играет каждая игра сама; касание, запустившее автомат (состояние 1 → 2), — событие владельца (и хоста тоже), остальные проигрывают его штатной коллизией для своей копии, по порядку, с повтором, пока автомат доигрывает прошлую монету; состояние хоста накладывается только на вышедший из цикла автомат (заклинил, взорвался). В живое сохранение модуль не пишет. *Открыто:* свои счётчики сохранения ведут и другие автоматы (батареечный попрошайка — №0x1ef), их выплаты случайны и играются только хостом — засчитывается ли гостю в штатной игре, проверить отдельно.
3. **Копия толкает товар магазина.** По разбору коллизии подбираемого (`0x2e8ae0`) `true` значит «столкновения нет», а `false` (физический толчок) функция возвращает только при `price == 0`: предмет с ценой не толкается никогда — ни при нехватке монет, ни при покупке; то же при взведённом ожидании `+0x54c`. Перехват отвечал за копию `false` всегда — копия пихала товар в тех играх, где она копия (а копия гостя на хосте двигала бы его для всех: место подбираемого — хоста). Теперь копия отвечает правилом игры.

Детектор расхождений (`Watch-IsaacNativeDivergence.py`) не назвал ни одной из трёх: он не сравнивал классы столкновений, слой отрисовки и места подбираемого. Добавлено позже 21 сентября 2026 (логика сравнения проверена на подставных снимках, живьём — нет): у врагов одного seed сверяются `+0x184`, `+0x188`, `+0x354`, у подбираемого — место (расхождением считается больше четверти клетки; называется в полуклетках, чтобы катящийся предмет не давал «устойчивого» расхождения).

### Вторая сессия пробы (21 сентября 2026, та же сборка с тремя правками магазина и помощью тестеру)

1. **Какашки босса у гостя не появлялись или оставались сломанными.** Чтение сетки обеих игр: у хоста сломанная какашка — у гостя декорация (ячейки 52, 68, 100); у хоста свежая какашка — у гостя щебень (63, 66: босс положил новую поверх сломанной). 2. **Хост ушёл на следующий этаж, гость остался.** Копия хоста у гостя люк не задела; после этого `OTHER FLOOR` рос у обеих сторон и ничто не сходилось. Сделано следование за этажом по образцу комнаты: тело несёт `floorEpoch`, игра, услышавшая строго более новую смену с другого этажа, просит штатный `Game::StartStageTransition` (`0x2fdc10`, найден по строке журнала «Starting stage transition»; `sameStage=0`, анимация 0 как у люка, игрок `nullptr` — игра сама берёт первого; защёлка `Game+0x1ba78`). Проверено чтением живых игр: защёлка в покое 0 (у хоста — после завершённого перехода), байты входа функции совпали. **Не наблюдалось вживую:** значение защёлки во время перехода — наблюдатель стоял, но гость в люк не зашёл до закрытия игр; что функция пишет туда 1, известно только из разбора. Следуется только обычный спуск: если после перехода этажи всё ещё разные (путь вверх, альтернативные этажи), это считается (`floorsElsewhere`) и не повторяется — иначе каждая попытка уводила бы на этаж ниже. Значит, синхронизация следов — это рождения эффектов с хоста событиями плюс блокировка собственных у гостя, перехватом слотов таблицы (не правкой `Game::Spawn`). **Два замера рождений (8 и 3 минуты, ~80 выборок/с, только чтение) боя не застали — данных о потоке крови нет.** Побочно: seed эффектов у сторон не совпал ни разу (сопоставлять нельзя — только блокировать и создавать); поле «кто породил» (`+0x3c8`) у эффектов пусто всегда, даже у брызг слезы игрока, — отличить эффект игрока от эффекта мира им нельзя, делить придётся списком видов. ### Третья сессия пробы (21 сентября 2026, 08:00–08:27; играл пользователь, семь этажей с помощью тестеру)

Пара на той же сборке, журналы и листы — `Binaries\native-test-results\probe-0.1.3c\`. **По слову пользователя работает всё из списка пробы:** магазин (потухший костёр, товар, табло автомата пожертвований), какашки босса, помощь тестеру (F6/F7/F8), спуск на этаж вдвоём. За 25 минут `faults 0`, `datagrams refused 0`, потерь 0; у гостя 496 смертей по слову хоста, 30 созданных врагов, 12 лишних ушли `Remove`, 59 зачисток с хоста, 2 рождённые ячейки. **Оговорка про этажи:** все шесть спусков обе игры сделали штатно сами, с разницей в несколько кадров (копия хоста задевала люк гостя) — `floors followed 0`, то есть **наше следование за этажом так ни разу и не сработало и живьём не проверено**. Детектор с новыми сравнениями назвал четыре расхождения, все сошлись сами за 1–4 с (места двух ключей после сундука, лишний ключ у гостя, сердце только у хоста).

**Падение гостя на седьмом этаже — причина найдена по памяти упавшего процесса, исправлено, собрано, живьём НЕ проверено.** Комната 1.890, три Needle (тип 881). В журнале гостя «Caught exception, writing minidump» (дампа игра не пишет — только копию журнала в `crash_dumps`); процесс висел на окне ошибки, и с него без вмешательства сняты стеки и полный дамп (`cdb -pv`; `guest-crash-stacks.txt`, `guest-crash.dmp`). Исключение — C++ `std::out_of_range` «invalid deque<T> subscript» на потоке игры: `Game::Update` → `Room::Update` → `Entity_NPC::Update` (слот 3 таблицы, `0x2c4b30`) → диспетчер ИИ `0x2c2990` (case 199) → ИИ Needle `0x14eb80` → `deque::front()` `0x99230`. У врага две очереди точек — след прыжка `+0xc04` и высоты `+0xc18` (размер очереди `+0x10`); при **собственном** переходе из состояния 3 в прыжок (6) игра обе чистит (`0x99380`) и кладёт в каждую первую точку (`push_back`, `0x99190`: место и `{0, V1.y}`), а в состоянии 6 каждый кадр берёт первую точку следа. В дампе у врага на стеке (seed `d33d9a98`) состояние 6 и **обе очереди пусты**, у его соседа — состояние 3: состояние 6 записал наш модуль со слов хоста, минуя вход в него. `faults` остался 0, потому что исключение случилось в обновлении самого врага, а не под защитой модуля.

Это общий изъян правила поведения: **состояние, записанное снаружи, пропускает всё, что код игры делает на входе в него** (до сих пор было известно только про анимацию). Сделано два слоя:

1. **Needle — как в игре:** близнецу, которого отправляют в состояние 6, модуль сначала чистит обе очереди и кладёт первые точки теми же двумя функциями игры (место и высота — хоста); байты входа обеих функций сверяются при старте. Счётчик `needleLeaps`.
2. **Общая страховка для видов, которые никто не смотрел:** у гостя `Entity_NPC::Update` идёт под защитой (перехват слота 3 тем же механизмом, что перехваты сетки; у хоста и до `LIVE` — штатно). Враг, чьё обновление бросило исключение, оборван посреди кадра: он уходит штатным `Remove`, через треть секунды список хоста создаёт свежего под тем же seed, а его вид (тип, вариант) до конца матча ведётся только местом и здоровьем — поведение своё. Часть составного врага не удаляется (остаётся как есть и может бросать снова — исключения ловятся). Счётчики `npcFaults`, `ownBehaviourKinds`; в `.status` — «enemies whose update threw», в стенде — `ENEMY UPDATES THROWN` сразу за `FAULTS`.

Основная сборка пересобрана после закрытия игр: 12/12 CTest, 54/54 Python. **Замер рождений эффектов этой сессии (38 минут, с боями) потерян:** при штатном закрытии игра обнуляет указатели раньше, чем уходит процесс, пробник упал с `InvalidState` (ждал только `OSError`) и отчёт не записал. `effects_births.py` исправлен — переживает любую ошибку чтения (200 подряд — конец) и пишет отчёт раз в минуту; для следов на полу замер нужно повторить.

Открыто: другие враги с собственными контейнерами, заполняемыми на входе в состояние, наверняка есть; страховка превращает их из падения в счётчик, и каждый такой вид стоит затем разобрать, как Needle. Ловля исключения оставляет глобальное состояние игры таким, каким его бросил оборванный кадр врага, — для `out_of_range` из ИИ это безвредно, для произвольного сбоя гарантий нет (альтернатива — верное падение).

**Следующая проба:** новая пара на пересобранной сборке — магазин (костёр не ранит гостя и монета поверх углей; копия не двигает товар; после монеты гостя число на табло растёт у обоих), затем бой с призывами (`npcSpawned` растёт после 48-го) и матч на троих с уходом игрока (`bodies applied` растёт после перезапуска). Пока тестовые игры открыты, основную сборку пересобирать нельзя; проверка компиляции — в отдельной папке `Binaries\authority-check`.

## Риски

- Править придётся код игры, а не только таблицы методов; бета обновляется часто, адреса надо будет искать по сигнатурам.
- **Изменённый сетевой код никогда не должен встречаться с обычными игроками**: только локальный сервис, а позже закрытые лобби с другим ключом протокола. До этого в Quick и Public Match с модулями не заходить вовсе.
- Локальный сервис — невыпущенный код, может быть неполным.
- Доверие владельцу означает, что нечестный клиент может всё; для игры с друзьями это приемлемо.
- Моды: расчёт своего персонажа у владельца переносит их без труда; моды, создающие сущности мира, видны остальным только в том объёме, который передаёт хост.
