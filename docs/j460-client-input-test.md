# Ввод клиента на хосте

**19 сентября 2026, 22:16 UTC: живой тест прошёл с первой попытки.** Команды, пришедшие по UDP, управляют настоящим игроком J460 через штатный код движения и стрельбы игры. Тест не нажал ни одной игровой клавиши. Это проверка главного архитектурного вопроса второй половины модели: может ли хост симулировать игрока по сетевому вводу, а не по позициям.

| Фаза (команда клиента) | Длительность | Смещение игрока хоста, x / y |
| --- | --- | --- |
| нейтраль | 0,5 с | 0,0 / 0,0 |
| вправо | 0,8 с | +175,1 / 0,0 |
| нейтраль | 0,7 с | +36,6 / 0,0 — торможение самой игры |
| влево | 0,8 с | −174,9 / 0,0 |
| нейтраль | 0,5 с | −35,9 / 0,0 |
| вверх / вниз | по 0,5 с | −92,0 / +60,1 по y |
| стрелять вправо | 0,9 с | 0 / 0,9; появились слёзы со скоростью вправо |
| вправо, затем **клиент молчит** | 0,4 с + 1,2 с | +70,8, затем остановка: через 700 мс тишины скорость нулевая |

Принято 390 команд, отклонено 0. Перехват подставил 3352 чтения значений, 2723 «нажато» и 1676 «только что нажато»; 11410 чужих запросов (другие контроллеры, меню, действия вне набора) прошли к оригиналу. Слёз без команды не было. Слот менеджера ввода восстановлен, ошибок сети нет. Summary: `Binaries/diagnostics/input/input-20260919-221651-006061.summary.json`, рядом — ряд наблюдений позиции.

Разгон и выбег в нейтральных фазах показывают, что работает именно физика игры: клиент передаёт только наклон осей, а ускорение, трение, скорость персонажа и темп стрельбы считает хост. Команда с осью больше 1 отвергается форматом — клиент не может попросить скорость выше полной.

## Второй игрок на хосте

**19 сентября, 22:37 UTC: получен и управляется по сети.** Пользователь подсказал, что локальный кооператив в игре — splitscreen. Наблюдение опросов менеджера ввода в первой комнате (режим `--observe`, ничего не подставляется) показало: кроме игрока с контроллером 0 игра дважды за кадр спрашивает у **контроллера 1** «только что нажато» для действия 19 — кнопки присоединения. Модуль ответил за этот контроллер сам.

| Шаг (команды для контроллера 1) | Игроков у хоста |
| --- | --- |
| нейтраль | 1 |
| «присоединиться» (действие 19), 0,3 с | 1 — открылся выбор персонажа |
| нейтраль 1,2 с | 1 |
| «подтвердить» (действие 14) | 1 → **2** |
| далее | 2; игра читает у контроллера 1 оси 0–7 и кнопки как у полноценного игрока |

Затем обычный сценарий ввода, но для контроллера 1: второй игрок прошёл +170,7 вправо, выбег 36,6, влево −166,1, вверх −92,0, вниз +55,9, стрелял вправо и остановился при молчании клиента; **первый игрок (клавиатура, контроллер 0) сдвинулся на 0,0**. Принято 388 команд, отклонено 0, тест не нажал ни одной клавиши, слот восстановлен. Summary: `input-20260919-223725-788179`. После перезапуска забега (R) у хоста снова один игрок — присоединение повторяемо, а адаптеры мира, рассчитанные на одного игрока, продолжают работать.

Первая попытка присоединения не сработала, и причина была в модуле: обработчик кооператива (RVA `0x5bac40`) в одном кадре спрашивает «только что нажато 19?» дважды — сначала для скрытой комбинации (присоединение + бомба + карта), затем для обычного присоединения. Модуль отдавал это событие один раз, и второй вопрос получал «нет». Настоящее устройство держит признак весь кадр; теперь нажатие, замеченное приёмником, ждёт первого вопроса игры и затем отвечает «да» в течение одного кадра (12 мс). Из того же кода: выбор персонажа присоединившегося управляется действиями 20/21 (влево/вправо), 14 (подтвердить) и 15 (назад).

**Ограничение.** Обработчик перебирает *существующие устройства ввода*, а не номера. Контроллер 1 опрашивался потому, что к ПК подключён геймпад. На машине без второго устройства игра не спросит о присоединении; там понадобится либо виртуальное устройство в списке менеджера ввода, либо прямой вызов создания игрока (кандидат — функция RVA `0x3a6450` из скрытой комбинации, не проверен).

## Как игра читает ввод (J460)

Привязки Lua (`Input.GetActionValue`, `IsActionPressed`, `IsActionTriggered`, `EntityPlayer.ControllerIndex`, `GetMovementInput`) дали всю цепочку; экспорт — `Binaries/research/j460-input*/`, профиль — `native/IsaacNetProbe/profiles/j460-input.json`.

| Назначение | Адрес или смещение |
| --- | --- |
| Номер контроллера игрока | `Entity_Player+0x1618`; у единственного игрока 0 (клавиатура) |
| `Entity_Player::GetMovementInput` / `GetShootingInput` | RVA `0x379360` / `0x379620` |
| Значение действия для игрока `(action, controller, entity)` / «нажато» | RVA `0x5562d0` / `0x556110` |
| Менеджер ввода / его виртуальная таблица | объект RVA `0x857b18` / таблица RVA `0x782950` |
| `WithDevice(controller, reader, in, out, deviceId)` | слот 29, RVA `0x620fb0`, thiscall, `ret 0x14` |
| Читатели: значение / «нажато» / «только что нажато» | RVA `0x620ab0` / `0x620940` / `0x6209e0` |

`0x5562d0` сначала даёт слово колбэкам модов (`MC_INPUT_ACTION`), затем, если контроллер равен −1 и есть сетевые устройства (`Manager+0x4b3d8`), опрашивает их виртуальный метод `+0x38`, иначе вызывает `WithDevice` менеджера ввода с номером контроллера и функцией-читателем. Читатель значения пишет float в `out` и возвращает «не ноль»; остальные возвращают bool. **Штатный онлайн тоже представляет удалённых игроков устройствами ввода** — это согласуется с выбранным направлением: хост симулирует, клиент шлёт ввод.

## Реализация

`IsaacAuthorityInput.dll` (`src/input_adapter.cpp`, чистая логика — `input_state.cpp`) меняет один слот виртуальной таблицы менеджера ввода — тем же приёмом, что слоты Update сущностей; код игры не патчится. Перехват отвечает сам, только если запрос идёт к управляемому контроллеру, читатель — один из трёх известных, действие — из набора (4 движения, 4 направления стрельбы, бомба, предмет, карта, сброс, присоединение, кнопки меню; пауза, карта уровня и рестарт остаются за устройствами хоста) **и есть свежая команда** (не старше 250 мс). Иначе решает настоящее устройство: молчащий клиент — нейтральный клиент, а не залипшая клавиша. «Только что нажато» ведёт себя как у настоящего устройства: нажатие, замеченное приёмником, ждёт первого вопроса игры и затем отвечает «да» на все вопросы в течение одного кадра.

Протокол INP1: 56 байт, little-endian — сессия, возрастающий номер, время, контроллер 0–7, четыре оси −1…1, маска кнопок. Проверяются размер, версия, резерв, конечность и диапазон осей, контроллер, сессия, порядок и свежесть. Только loopback, сессия до 30 секунд.

```powershell

.\scripts\Install-IsaacRoom.ps1 -Stage Input
python scripts/Test-IsaacInput.py --pid <HOST_PID> --restart-run --binary-directory '<папка игры>\IsaacAuthority\Input'
```

**11/11 CTest и 24/24 Python-теста проходят**, включая кнопки присоединения и меню и запрет на паузу, карту и рестарт от клиента. Новое: кодек INP1 на двух языках, отображение осей в действия, порог нажатия, защита от осей больше 1, повторов, чужой сессии и устаревших команд, контракт модуля.

## Что это даёт и что остаётся

Ответ на архитектурный вопрос положительный: у ввода одна узкая точка, подстановка идёт по номеру контроллера, и игра симулирует такого игрока сама. Стены нет.

- **Присоединение без второго устройства.** Второй игрок получен штатным локальным кооперативом, но игра опрашивает присоединение только у существующих устройств (см. выше).
- **Сторона клиента.** Тот же перехват в режиме чтения: брать ответ настоящего устройства для контроллера 0 на клиенте и отправлять хосту. Не сделано.
- **Сведение с репликой мира.** Снимок с обоими игроками сделан следующим этапом: [два игрока в снимке мира](j460-coop-players-test.md). Остаётся клиенту предсказывать своего игрока (как в стенде `IsaacAuthorityLab`).
- Проверены оси ±1 и кнопки «присоединиться» и «подтвердить»; бомба, предмет, карта, сброс и аналоговые значения между 0 и 1 — нет.
