# Подключение авторитетного хоста к J460: первый этап

**Последнее обновление:** [жизненный цикл обычных слёз](j460-world-tears-test.md) проверен 19 сентября, 20:38 UTC: 3 создания/удаления, 194 точных применения, удержание при паузе, очистка при контрольном новом epoch комнаты. Самого перехода комнаты ещё нет. Ранее [реплика одного игрока между двумя J460](j460-game-pair-test.md) прошла с 271 точным применением. Выбранный игрок и созданные копии слёз не исполняют собственное обновление на клиенте; остальная симуляция пока независима. Ниже — результаты раннего этапа и общий порядок интеграции.

Предыдущие этапы: [чтение игроков и UDP-наблюдатель](j460-live-state-reader.md), локальный сдвиг X и [пять состояний от тестового отправителя](j460-network-state-test.md).

Выполнен [локальный тест коррекции после обновления игрока](j460-player-step-test.md): 127 обновлений при наблюдении и 244 при разовом сдвиге X на +8; следующее обновление сохранило новую позицию, слот оба раза восстановлен. Смена комнаты и уничтожение игрока ещё не проверены.

## Реализованный результат

Добавлен [самостоятельный C++-стенд](../native/IsaacAuthority/README.md): авторитетное движение двух игроков, предсказание, коррекция, ограниченные очереди и UDP между двумя процессами. Это проверка нового способа синхронизации, не исправление или замена сетевого кода внутри установленного Isaac.

Проверка 18 сентября 2026 прошла MSVC x86 Release, `/W4 /WX`:

- Модель сети: 900 шагов хоста, клиент остановлен на 180 шагов, пропущено 668 отправок ввода, 82 коррекции; конечные состояния совпали.
- Два реальных процесса: 400 шагов за 4004 мс, клиент остановлен на 80 интервалов, пропущено 57 отправок ввода и 36 снимков хоста; конечные состояния совпали, неподтверждённых команд не осталось. Счётчики UDP могут меняться от планирования ОС.

## Что установлено по игровому коду

Проверенный SHA256 J460: `3bdfc8bae0dc7e334b76009d0ad45dfbb16ee5f00c06ffbc3a0094e34d44616b`. Скрипт `reverse/ghidra/ExportIsaacAuthority.java` экспортировал восемь функций из существующей базы Ghidra; результаты находятся в `Binaries/research/j460-authority/`. Анализ статический: прототипы, ABI и поля требуют проверки в debugger.

| RVA | Наблюдение в декомпиляции | Статус |
| --- | --- | --- |
| `0x501190` | Поиск записи ввода по номеру кадра, возврат адреса полезной нагрузки записи | Статический кандидат |
| `0x501070` | Копирование четырёх 32-битных слов записи ввода в ограниченную таблицу | Статический кандидат |
| `0x501cb0` | Вызывается при подготовке устройств ввода, использует поиск/вставку записи | Роль требует уточнения |
| `0x510980` | Обходит устройства и дополнительные очереди; при невыполненных условиях возвращает false до дальнейшей обработки | Кандидат сетевого барьера шага |
| `0x511120` | Обновление сетевых очередей, вызывает вставку записей | Роль требует уточнения |
| `0x355470` | Инициализация игрока, подтверждена ссылкой на строку журнала | Статический кандидат |
| `0x502010` | Получение ввода, отбрасывание старых/повторных кадров | Экспортирован ранее и повторно как вызывающая функция |
| `0x502950` | Отправка ввода локального игрока | Экспортирован ранее и повторно как вызывающая функция |

В `0x510980` собирается результат обработки устройств и готовности дополнительных очередей; ранний возврат при неготовности подтверждает направление поиска барьера. Это не доказательство, что достаточно заменить один return: вызывающий игровой цикл и жизненный цикл объектов ещё не восстановлены.

В отправке/приёме видна 16-байтовая запись: номер кадра u32, пять полей u16 и два u8. Семантика кнопок/осей пока не установлена; нельзя выдавать эти поля за проверенную структуру управляющего ввода.

При первом экспорте строки форматирования pre/post не дали готовых функций; последующий адресный анализ восстановил пути `0x4fe3a0` и `0x4ffc70`. Внешнее чтение координат/скоростей, коррекция и источник/реплика одного игрока уже проверены (см. обновление выше). Режим реплики всего мира **ещё не реализован**. Смещения из REPENTOGON J273 нельзя переносить в J460 без проверки.

## Порядок интеграции

1. Восстановить цепочку игрового шага и перечисление игроков для J460. Проверить ABI и чтение положения/скорости на главном потоке в локальном забеге; сопоставить с игровыми данными.
2. Проверить применение позиции/скорости на границе шага локального теста. Отдельно проверить смену комнаты и уничтожение игрока, чтобы не сохранять устаревшие указатели.
3. Добавить отдельный режим реплики: хост считает мир, клиент не принимает самостоятельных решений о попаданиях, наградах и создании объектов. Только после этого связывать снимки с протоколом.
4. Два игровых процесса в одной пустой комнате: хост продолжает симуляцию при остановке клиента, клиент возвращается к состоянию хоста. Сверить не только координаты, но и отсутствие двойных игровых событий.
5. Затем расширять состояние: стабильные ID/поколения сущностей, появление/удаление, враги и снаряды, предметы/урон, согласованная загрузка комнат. Клиентское предсказание потребует настоящей модели движения и коллизий; тестовая `StepFixture` для игры не подходит.

Текущая диагностическая DLL и игровой EXE не изменены этим этапом. Запускать игру пользователю для проверки сетевого стенда не требуется.
